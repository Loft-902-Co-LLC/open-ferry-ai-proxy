# Changelog

All notable changes to open-ferry are recorded here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and open-ferry follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, a minor version may change behaviour.

Where open-ferry differs from CLIProxyAPI, which it ports, is in [UPSTREAM.md](UPSTREAM.md). How to move over is in the [migration guide](docs/migrating-from-cliproxyapi.md).

## [Unreleased]

The first release, 0.1.0, isn't out yet. The releases below are candidates for it, published to test updating from one signed release to the next. This is what is in place today, ported from CLIProxyAPI v8.0.38.

### Added

- **Source-bound config-save parity proofs** independently track upstream relocations and generated archives, retaining strict checks for deleted identities, comment counts, values, and output bytes.

- **Offline differential parity in CI** runs handwritten cases and a fixed-seed random set against the pinned CLIProxyAPI source in required checks, with larger daily and manually seeded runs and retained synthetic failure artifacts ([parity in CI](tools/parity/README.md#in-ci)).
- **Repeatable parity suite filters** select named suites with `open-ferry-parity --suite`; unknown names are rejected before running Go.
- **Claude tool-closure and embedded JSON comparisons** recognize independent closures within each provider event and compact object-valued text only at documented translator paths with raw-request provenance.
- **Upstream defect proofs** count source-preserved comment and scalar losses and failed-write counterfactuals separately, retaining the original Go output and requiring complete output checks.

- **Vertex AI OpenAPI routing overrides** per model and credential, with explicit OpenAPI locations in both configuration layouts and service-account auth files; explicit `false` values survive saves, a deviation from upstream's insertion pruning.

- Real-server dashboard journeys in the required Ubuntu CI aggregate, covering first run, config saves, credentials, a loopback provider, usage, restart persistence and plain-install updates.
- **Ingress resource limits**, open-ferry additions for both listeners: bounded connections and aggregate request-body storage, header and TLS handshake deadlines, upload progress and total deadlines, idle HTTP/2 GOAWAY, and stalled-response protection. Long SSE streams and upgraded WebSockets remain supported. Defaults, overrides and reload behavior are in [configuration](docs/configuration.md#ingress-limits-open-ferry-additions).

- **Vertex AI partner and open models through `endpoints/openapi`**, with credential-declared model names and aliases; static keys require a configured endpoint attribute.
- **Meta Responses remote compaction v2**, with sealed CPA summary capsules, replay and local token counting.
- **Claude web search result caching for Responses sessions**, opt-in and isolated by session, caller and selected credential, with entry limits, sliding expiry and invalidation when its settings change.
- **Meta Muse reasoning-envelope recognition and replay** through Gemini and Interactions clients.
- **Management model definitions fall back to sorted available registry models**, including configured OpenAI-compatible provider channels.
- **CLIProxyAPI's `config.yaml` and auth directory, read as they are**, in both the legacy and the v8 layout. Changes to either are picked up without a restart.
- **Sign-ins** to Codex (`-codex-login`, or `-codex-device-login` with a device code) and to Claude (`-claude-login`).
- **Sign in with ChatGPT for Codex credentials.** `-siwc-bind FILE` adds a second login, with ChatGPT, to a Codex credential's file, and so does **Add OpenAI API access** on the dashboard's Credentials page. While the credential's `use_siwc` is on, Responses calls go to the OpenAI API (`https://api.openai.com/v1`, or its `base_url`) with that login's token, in place of ChatGPT's Codex backend with the usual one. A missing SIWC login is a 401 for Responses; the usual token is never sent in its place. ChatGPT Alpha Search instead requires the original outer OAuth token and returns a local 401 when it is missing, even if a SIWC login is present. `POST /v8/management/oauth/siwc/bind` starts a bind, and v8 credential listings expose `siwc_bind_supported`, `use_siwc`, `siwc_bound` and optional `siwc_expires_at`. Bindings and sign-ins saved during shutdown load on restart; the dashboard explains bindings stopped by shutdown or refused because the server is busy. The steps are in [docs/cli.md](docs/cli.md#binding-sign-in-with-chatgpt-to-a-codex-credential).
- **Local Sign in with ChatGPT status.** `GET /v8/management/oauth/siwc/status` and `GET /v8/management/credentials/siwc/status` report `off`, `valid` or `invalid` without refreshing or contacting a provider; v8 Codex credential listings include `siwc_status`. Status uses real expiry and remembers a rejected SIWC bearer across outer refreshes, sign-ins, toggles and same-token binds or refreshes until that nested bearer changes.
- **The client APIs**, over HTTP and WebSocket, sending each part of a streamed answer as soon as it's ready, as CLIProxyAPI does:
  - OpenAI Chat Completions, legacy Completions and Responses;
  - Claude Messages;
  - the Gemini API's `/v1beta/models` routes, and Gemini Interactions;
  - the model list Codex clients fetch.
- **The images endpoints**, `/v1/images/generations` and `/v1/images/edits`: the Codex image generation tool's models (`gpt-image-1.5`, `gpt-image-2` and the `gpt-image-2.5` ones) through Codex credentials, on `gpt-5.4-mini` or the model `gpt-image-2-base-model` names; xAI's Grok Imagine image models through `xai-api-key` credentials, which now list them; and the image models of `openai-compatibility` providers. An edit can be a `multipart/form-data` form, read in memory up to the body limit and never written to disk. `disable-image-generation: true` turns both endpoints away.
- **The video endpoints**, served by xAI's Grok Imagine Video for `xai-api-key` credentials: xAI's own `/v1/videos` routes, and OpenAI's `/openai/v1/videos` with a video's status and its content. Later calls about a video go to the key that made it, remembered in memory for `video-result-auth-cache-ttl` (three hours by default). The video is streamed to the client, never written to disk.
- **The speech endpoints**, OpenAI's `/v1/audio/speech` and xAI's `/v1/tts`, served by xAI's Grok TTS models (`grok-tts`, `grok-voice-tts-1.0`) for `xai-api-key` credentials. Either takes OpenAI's request or xAI's; OpenAI's voices and speech models stand for Grok's, and the audio comes back as MP3, WAV or PCM. The other routes refuse the speech-only models with a 400.
- **The providers**: Codex, Claude, Gemini, Gemini Interactions, Vertex AI, Meta (API keys and access tokens), xAI (API keys) and any OpenAI-compatible upstream. Requests are translated between the client's format and the provider's.
- **`claude-cli`**: Claude models through your own installed Claude Code, which open-ferry runs for each request. Claude Code signs itself in to your subscription and makes the requests to Anthropic; open-ferry stores no token for it. Each entry of the config's `claude-cli` list is one Claude Code account. The dashboard's Credentials page shows each entry with its state, cooldown, last error and quota windows, and checks whether it is signed in when asked to (the dashboard API's `claude-cli/entries` and `claude-cli/auth-status` routes). The Claude sign-in (`-claude-login`), by contrast, goes against Anthropic's terms, gets only the Haiku models in our testing and puts the account at risk, so the docs now warn about it. See [docs/claude-subscription.md](docs/claude-subscription.md).
- **CLIProxyAPI's credential manager**: it picks an account for each request, retries on another, handles cooldowns and quota, applies model aliases, and refreshes tokens in the background.
- **Routing by quota**, open-ferry's own: `routing.strategy: quota` picks the Claude, `claude-cli` or Codex credential by the quota windows the provider last reported, the one whose limit resets soonest (`routing.quota.prefer: soonest-reset`, the default) or the one with the most left (`most-left`), keeping back `routing.quota.reserve-percent` of each window while another credential has room. Credentials with no reading, such as API keys, count as having all of their allowance left. CLIProxyAPI runs this strategy as round-robin ([docs/routing.md](docs/routing.md)).
- **A cap on long quota rests**, open-ferry's own and off by default: with `routing.quota.check-after: 1h`, a credential the provider says is out of quota for longer rests an hour, then one request is let through to check; each check the provider refuses doubles the wait, never past its reset. The management API's `auth-files` entries show when the next check is, as `quota_checks`, and `save-cooldown-status` keeps the rests across a restart ([docs/routing.md](docs/routing.md#a-cap-on-long-quota-rests)).
- **The management API subset T3 Code uses, and more**, under `/v0/management` and `/v8/management`:
  - credential files and their state;
  - the OAuth logins;
  - reads of the config;
  - logs, usage and quota fetches.
- **Config writes through the management API**: the settings, the client and provider key lists, the OAuth lists and `config.yaml` under `/v0/management`, and the writes of `config`, `config.yaml` and a path in the config under `/v8/management`, including turning a config API key off or on. A save keeps the file's comments, its key order and the settings open-ferry doesn't type, holds an exclusive lock on `config.yaml.lock` from its read to its write, the same lock `open-ferry config` takes, waiting at most 5 seconds for it, replaces the file in one step with the previous one kept as `config.yaml.bak` and the SHA-256 of what it wrote recorded in `config.yaml.sha256` (or, for a file that can't be replaced so, such as a config bind-mounted on its own into a container, writes over it in place, as CLIProxyAPI does), and takes effect before the request is answered. On Windows, replacement retries briefly when another program holds a file open without allowing replacement. A save that fails changes nothing. A save of a setting, a list or a key's status made after the file changed on disk since the server loaded it, as by `open-ferry config` or a hand edit, writes nothing and answers 409 `config_changed`; the server loads the file again, so the save made again keeps that change. A file it can't load, such as an empty one, is left out, the management API keeping the config the proxy runs, and each such save answers 409 until the file is fixed.
- **Request logs, `main.log`, usage records, payload rules and saved cooldowns**, as CLIProxyAPI has them.
- **CLIProxyAPI's terminal UI** (`-tui`), as a client of a running server's management API (`-management-base-url`) or of one it starts (`-standalone`). Its OAuth tab offers Codex and Claude. Unlike CLIProxyAPI's, it doesn't follow a redirect, so the management key goes only to the address given.
- **`-password`**, a management password for clients on the same machine, with CLIProxyAPI's `/keep-alive` endpoint.
- **`open-ferry init`**, which writes a starting config: the example config with a new client key and management key, listening on 127.0.0.1 only, at `-config` or the installed config path. It prints the keys once, and replaces an existing config only with `-force`, keeping the old one as `.bak` ([docs/cli.md](docs/cli.md)).
- **`open-ferry check`**, which looks over a setup before a start: the config, safe mode, the keys, the auth directory and its credential files, TLS, whether the port is taken, the dashboard, the clock and each `claude-cli` entry's Claude Code. It prints a line for each finding with what to fix, or JSON with `-json`, and exits with 0, 1 for an error, or 2 when it couldn't check. It writes nothing and makes no network call beyond loopback.
- **`open-ferry service`**, which installs open-ferry as a background service that starts again when it fails, and removes it: a systemd unit on Linux, a launchd job on macOS and a scheduled task at logon on Windows, or with `-system` a service for the whole machine. `-dry-run` shows what it would do ([docs/cli.md](docs/cli.md#open-ferry-service)).
- **Commands to look at and change a setup**, for people and coding agents: `open-ferry status`, `config get|set|unset|show|diff|undo|replace`, `keys list|add|remove`, `credentials list|enable|disable|reset-quota|remove|login` and `clients setup`. Each prints text, or one JSON object with `--json`, and exits with a code an agent can act on. With a server running for the config, a change goes through its management API and applies at once; with none, it is written to the file with the same checks and writer. Every change lists what it changed, old and new values masked, and `config undo` reverses it, through the dashboard API's new `POST /open-ferry/api/v1/config/undo` while a server runs. An undo of a file changed since the last write, as by a hand edit, is refused unless confirmed (`changed_since`; `409 changed_since` from the route without `force`), and one whose file or backup changed after it was shown is refused (`config_changed`; `409 config_changed` from the route, which `config undo` sends the SHA-256 of both); its answer when it needs `--yes` gives both (`config_sha256`, `backup_sha256`), and `--expect-backup-sha256` (`expect_backup_sha256`), given with `--expect-sha256`, ties the confirmation to the backup shown too. Deleting, showing a secret, replacing the whole config and changing a sensitive setting (`management.allow-remote`, `secret-key` and `separate-address`, `server.host` off loopback, `server.tls`, `server.trusted-proxies`, the last client key, counted as the server counts keys so blank and repeated ones don't count) need `--yes`, and without a terminal nothing is changed; the answer then gives the SHA-256 of the config it was worked out from (`config_sha256`), and `--expect-sha256` (`expect_sha256` for a tool) given with `--yes` makes the change only to that config, refusing it with `config_changed` once the file has changed. A change through a server that runs a copy of the config, another file with the same bytes, says the file here didn't change. An error never repeats a flag that names a secret, nor an unknown subcommand or argument. Secrets are masked in everything they print, the auth directory's tokens included (one shorter than 8 characters wherever it is a whole word; in JSON only in strings and in the keys of what a setting holds, keeping keys made the same as `[redacted] (2)`, never in the answer's field names, nor in the hint that says how to go ahead with a confirmation), and never taken as arguments; a value `config set` reads from a file or standard input shows only as `"[redacted]"`, not even its keys; a config or value that doesn't load is said not to, and where (a line, a setting), never quoted; a file is read only for a secret, and never from the auth directory or a credential file (`unsafe_file`: one with a PEM block, or with a sign-in's or a key's field, such as `access_token`, `accessToken` or `tokens`, at any depth up to 32 levels, or, as one that can't be checked, one nested deeper, or that is neither one line of plain text nor a YAML or JSON mapping or list that reads without loss), and a tool call that reads one needs `confirm: true`; the management key comes from the config, `MANAGEMENT_PASSWORD` or a key file ([docs/cli.md](docs/cli.md#looking-at-and-changing-a-setup)). A server at the config's address is used only when the file it runs (`GET /v0/management/config.yaml`) holds the same bytes as the config, so one running another config on that port is never changed (`other_config`), and a change is written only to the file it was worked out from: worked out again when the file changed under it, and refused (`config_changed`) when it then needs a confirmation, whatever `--yes` said. A flag whose name names a secret (`--token=...`) is refused, and an unknown flag is named without its value. `keys add` and `keys remove` in the file add to or remove from the list the file holds then, so a key another write added or revoked meanwhile stays so; `keys remove` through a server reads the list again after removing by index, and says so (`key_list_changed`) when another write meant some other key went.
- **An MCP server**, `open-ferry mcp`, which serves those commands as tools on standard input and output, for Claude Code, Codex, T3 Code, Cursor and other agents' apps: the same checks and JSON, `confirm: true` in place of `--yes`, and no tool that returns a secret already in the setup; a sign-in still going when `credentials_login` stops waiting is a result saying to call again, not a tool error ([docs/mcp.md](docs/mcp.md)).
- **Updates**, open-ferry's own: the server looks for a newer release every six hours (`self-update.check-every`), checks its signature (each release's `SHA256SUMS` is now signed with minisign, as `SHA256SUMS.minisig`) and its SHA-256, and gets it ready. A supervised service, as `open-ferry service install` and `migrate` set up when the install can update itself, switches to it with no downtime: a blue-green supervisor starts the new version beside the old, moves traffic to it while requests in flight finish, and rolls back when it fails its watch. In `auto` mode it does this on its own; `open-ferry update` and `-rollback` ask for a switch, and `-check` shows the supervisor's state. In the plain form, `open-ferry update` installs it in place of the binary, keeping the old one for `open-ferry update -rollback`, and nothing is restarted on its own. Only a binary the install scripts put in place replaces itself, as the install receipt they now write says; any other, such as the container image's, only says when a release is out. Turn updates off with `open-ferry update -mode off`, `self-update.mode: off` in the config, `OPEN_FERRY_SELF_UPDATE=off` in the environment, or the install scripts' `--no-auto-update` (`-NoAutoUpdate`); `notify` only says when a release is out. `open-ferry -version` prints the version, `open-ferry check` reports on updates, the dashboard's About page shows their status with a check now, and Install now and Roll back for a supervised service, and its Settings page turns them off, and the dashboard API has the status, a check now, and the install and rollback ([docs/updates.md](docs/updates.md)).
- **`open-ferry migrate`**, which switches a CLIProxyAPI setup to open-ferry, on CLIProxyAPI's own config and auth directory, in place. It finds CLIProxyAPI and what starts it (a systemd unit, a launchd job, `brew services` among them, a Windows service, a scheduled task, a launcher or a container), says what carries over and what doesn't, warns that Claude sign-ins get only the Haiku models, and says what stops the switch, such as remote storage. With your yes, or `-yes`, it backs up the config, its `.env` files and the auth directory, writes a record of the switch with no secrets in it, and replaces CLIProxyAPI's service with open-ferry's or, for anything else, puts open-ferry's binary in place of CLIProxyAPI's. It then checks that open-ferry answers on the config's address, and undoes the switch when it doesn't. For a container, it prints the Docker Compose steps and changes nothing. `-dry-run` and `-json` only show the plan, and `migrate -undo` switches back, leaving the config and credentials as they are unless `-restore` is given ([migration guide](docs/migrating-from-cliproxyapi.md#switching-over), [docs/cli.md](docs/cli.md#open-ferry-migrate)).
- **A web dashboard** at `/dashboard/`, built into the binary, in place of CLIProxyAPI's downloaded control panel: `/management.html` sends the browser there. It signs in with the management key, and reads the management API and an API of its own under `/open-ferry/api/v1/` ([docs/dashboard-api.md](docs/dashboard-api.md)). It shows each credential's state, with the reason and what to do, the failing and resting ones first, and when a capped quota rest is next checked, and uploads, signs in, turns off, resets and deletes credentials; it also shows usage, searches the request logs, and gives client setups. Its Settings page edits the common settings, routing by quota, updates and the management address among them, the client API keys and `config.yaml`, with a review before each save, and asks before you leave with changes unsaved. On a first run its Overview replaces the example client keys with a new one in one step, taking the proxy out of safe mode; once a client has connected, it leads with today's calls and each account's health. It works on a phone as well as on a desktop.
- **A management address of its own**, `management.separate-address`, a setting of open-ferry's own: set to an address such as `127.0.0.1:8318`, it serves the management API, the dashboard and the dashboard API there alone, and the proxy's port answers every one of their paths with a 404, so it has no management route at all. Both addresses use `server.tls`, and a change takes a restart. `open-ferry check` looks for something already listening there and warns when `management.allow-remote` doesn't fit the address, and the TUI connects there by default. CLIProxyAPI ignores the setting and serves its management API on its port ([docs/dashboard-api.md](docs/dashboard-api.md#serving-the-app)).
- **A usage ledger**, `open-ferry-usage.sqlite3` in the log directory, which keeps the usage records for the dashboard while `usage-statistics-enabled` is on: 90 days by default, with no prompt or answer text and no client key in clear. Costs are estimated from prices you enter. The file is opened on a thread of its own, so the server starts serving without waiting for it; the records made meanwhile are kept.
- **Release binaries** for Linux (x86-64 and arm64, with glibc 2.31 or newer, and static ones that need no C library, for Alpine and older systems), macOS (Intel and Apple silicon, macOS 11 or newer) and Windows (x86-64). Each release comes with `SHA256SUMS` and build provenance attestations, and each archive lists the licenses of the Rust crates and npm packages built into it.
- **Install scripts**, `install.sh` for Linux and macOS and `install.ps1` for Windows, run with one line from the latest release. They pick the build for the system, refuse an archive that doesn't match `SHA256SUMS` or, when the GitHub CLI is installed, its attestation, install the binary in the user's own directory, and write a config with `open-ferry init` when there's none. They change no profile and no `PATH`. They then look for CLIProxyAPI and, when they find it, offer to switch it to open-ferry with `open-ferry migrate`, writing no config of their own then; `--migrate` (`-Migrate`) or `OPEN_FERRY_INSTALL_MIGRATE=yes` switches without asking, for unattended installs, and `--no-migrate` (`-NoMigrate`) doesn't look.
- **A container image**, `ghcr.io/loft-902-co-llc/open-ferry`, for linux/amd64 and linux/arm64, with CLIProxyAPI's image's paths, so that a Compose file switches by changing its image, and a `docker-compose.yml`. Its time zone is UTC, where CLIProxyAPI's is Asia/Shanghai, and the Compose file publishes only the proxy's port, on 127.0.0.1 ([migration guide](docs/migrating-from-cliproxyapi.md#docker-compose)).
- **Parity results in the README**, written by `tools/parity` with its new `--summary` option: CLIProxyAPI's version, and each suite's cases and outcomes.
- **A benchmark**, `tools/bench`, which runs open-ferry and CLIProxyAPI in front of the same fake upstream on loopback and measures start time, throughput, latency, CPU time and memory ([docs/benchmarks.md](docs/benchmarks.md)). It sends each provider requests in its own format and translated ones (Chat Completions to Claude, Claude Messages and Responses to an OpenAI-compatible provider), checks that the fake upstream gets each in its own format, and says how much time each proxy adds to the upstream's. `--machine-note` describes the machine in the report, which also gives the kernel and the Rust and Go toolchains, and `tools/bench/cloud/run-ubuntu.sh` sets up a fresh Ubuntu 24.04 machine and runs it there.
- **A setup page for coding agents**, [docs/agents.md](docs/agents.md), and an [`llms.txt`](llms.txt) that points to it.

### Changed

- **Fewer streaming allocations** per event for Chat Completions and Claude Messages, and no commit-header allocation when pre-first-token keepalive is disabled. Shared-host measurements did not establish an end-to-end speedup.
- **Config writer refusals** now answer `409 config_unwritable` with a safe reason. The CLI shows that reason, says nothing was changed, and distinguishes the refusal from an I/O failure in JSON output.
- **Smaller, faster release binaries**, built with fat link-time optimization and one codegen unit: about 11% less CPU per request and 31% smaller in the measured Linux build.
- **Ported from CLIProxyAPI v8.0.38**, up from v8.0.36. What the move left out, and why, is in [UPSTREAM.md](UPSTREAM.md#what-moving-from-v8036-to-v8038-left-out).
- **Dynamically registered Vertex OpenAPI models** advertise publisher ownership and default reasoning levels when explicit/static support is absent.

- **Codex clients get direct tool mode on synthesized or non-Codex routes**, with Responses Lite and reasoning-effort updates disabled; pure-Codex template capabilities stay intact.
- **Ported from CLIProxyAPI v8.0.36**, up from v8.0.32. What the move left out, and why, is in [UPSTREAM.md](UPSTREAM.md#what-moving-from-v8032-to-v8036-left-out).
- **Refresh outer Codex credentials 96 hours before nominal expiry.** Rejected unexpired JWTs and stream 401s recover in the background while sibling models remain blocked; SIWC keeps its independent five-minute lead.
- **xAI forwards the real downstream User-Agent**, with open-ferry as its default.
- **Ported from CLIProxyAPI v8.0.32**, up from v8.0.27. What the move left out, and why, is in [UPSTREAM.md](UPSTREAM.md#what-moving-from-v8027-to-v8032-left-out). It brings:
  - **Closed HTTP/2 connections are retried as transient drops**: a call that meets a connection the peer closed fails over to another try and no longer counts against the credential. A recorded `tls handshake timeout` message alone no longer counts as a transient failure.
  - **A model's own cooldown stays beneath a credential-wide quota cooldown**: when the credential's quota runs out, the model's cooldown is kept and comes back when the credential's ends. It is saved with `save-cooldown-status`. A success from a call dispatched before a cooldown no longer clears it.
  - **`If-Match` on v8 config writes**: reads of the v8 config routes answer an `ETag`, and a write that sends `If-Match` is refused with a 412 `precondition_failed` when the file has changed since. A write without it works as before.
  - **Vertex AI and Gemini fixes**: a Vertex AI key's base URL can carry the full `/publishers/` prefix; a Vertex AI request no longer ends on a thought-only model turn; a Gemini call that finishes with a malformed function call gives a Claude client a retryable error; a Gemini Responses call can use a client's tool search; a Claude client's non-streaming Gemini replies number their tool calls across replies, so two replies no longer both name a call `<name>-1`.
  - **Sign in with ChatGPT drops `configuration_update` items**: a Codex call over a Sign in with ChatGPT login drops the client's `configuration_update` input items, which that API rejects, and sends the last effort they set as the request's `reasoning.effort`, unless the model name's suffix already set one. A `response.steer` on Codex's WebSocket drops them without changing the effort.
  - **Gemini tool arguments are cleaned against the Claude tool schemas the client sent**, so the placeholder that schema normalization adds to a closed object no longer reaches the client's tool.
  - **Gemini schemas keep their unions**: a tool schema's multi-branch `anyOf` or `oneOf` stays a union, its `null` branches make it nullable, a branch that only lists `required` names gets the parent's properties it names, and the `discriminator` keyword Gemini rejects is dropped.
  - **Claude**: on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1, signed thinking replayed from earlier turns is sent with `thinking.block_binding.prefix_mismatch_behavior` set to `drop_block`, with the beta it needs; an assistant prefill to Haiku 5 or later is refused; a Chat Completions call to Claude gets the model's registered `max_tokens`; a Responses tool output marked incomplete reaches Claude as a `tool_result` error; Claude's tool search keeps the first deferred tool's cache anchor.
  - **Stream and usage fixes**: a Codex event split across `data:` lines is put together before it is translated; Codex tool schemas lose integer bounds outside the 64-bit range; xAI calls lose the web search options its Responses API rejects; a Meta client that leaves after the last event is a normal end; fallback item IDs in Interactions streams are unique.
  - **New config keys, carried and reported as ignored**: `requests.tls-handshake-timeout-seconds`, `upstream.claude.session-date-pin-days` and the four `claude-header-defaults` fields (`anthropic-beta-strip`, `anthropic-beta-append`, `inject-diagnostics`, `client-request-id`) load and save in both layouts, and `open-ferry migrate` reports them. They belong to client impersonation, which open-ferry doesn't do.
  - **The model catalog** is v8.0.32's, with Claude Haiku 5.5, Gemini 3.8 and Gemini 4 Argon, and Meta's Muse Wonder models.
- **Ported from CLIProxyAPI v8.0.27**, up from v8.0.20. What the move left out, and why, is in [UPSTREAM.md](UPSTREAM.md#what-moving-from-v8020-to-v8027-left-out). It brings:
  - **Sign in with ChatGPT for Codex credentials**: a Codex credential can hold a second login, with ChatGPT, and then calls the OpenAI API with it. It is under Added.
  - **Codex clients' `tool_search` on Claude**: a Responses call from a Codex client to a Claude model can use Anthropic's native tool search, which keeps the prompt cache prefix stable as the client finds tools. It is off by default. Turn it on with `upstream.claude.tool-search` (`claude.tool-search` in the legacy layout); a Claude key with a base URL other than Anthropic's also needs `native-tool-search: true`. Where it is on, the model list tells Codex clients which Claude models take it. A credential that can't take it gets the plain translation, as before.
  - **`response.interrupt` on the Responses WebSocket**: a client can interrupt a response that is running, over Codex's connection or in a turn run over HTTP. Codex and xAI WebSocket sessions now survive a config reload, and are closed only for a credential that is removed.
  - **`routing.session-affinity-rebind-on`**: with `quota`, a session keeps its credential through a transient failure, such as a timeout or a 5xx, which fails over for that call only, and moves on a quota, sign-in or model error. The default, `any`, is as before.
  - **`max-request-body-bytes`**: a request body that says it is longer than the limit gets a 413 before anything reads it, and the Responses WebSocket's messages are held to it too. Unset, zero or negative keeps 64 MiB, where CLIProxyAPI turns the limit off.
  - **`streaming.send-keepalive-before-ft`**: with it on and `streaming.keepalive-seconds` above zero, a stream sends its heartbeats before the first token.
  - **Vertex AI native Interactions**: a Vertex AI key or service account file with `interactions: true` sends an Interactions client's calls to Vertex AI's own Interactions API, at the global location, in place of `generateContent`.
  - **Responses compaction on Claude**: a compaction call for a Claude model has Claude write the summary, and returns it sealed, in the same format CLIProxyAPI uses.
  - **The Codex model catalog** no longer needs a `gpt-5.5` entry: without one, the first entry is the template for models that have none of their own.
  - **Usage records** say which client key provider let the call in (`access_provider`, `config-inline` for a key from the config) and whether the key is native (`is_native_key`). The usage ledger keeps both.
  - **Smaller fixes**: Claude's rate-limit parsing ignores overage billing resets; Claude's cache markers are counted, normalized and placed with invalid and null `cache_control` entries ignored; a Responses call to Claude respects the registry's completion limit for its default `max_tokens`; a Claude stream sends its message delta with the trailing usage; tool call IDs that Claude can't take are normalized, and Codex Chat Completions shortens over-length ones; Gemini's schemas lose the dependent keywords it doesn't support, and a function response with media gets a trailing user turn; Meta keeps foreign encrypted reasoning in Responses requests; Codex image requests keep the resolved upstream model; a canceled stream keeps the cooldown its upstream error set, and `credential_quota` counts as a quota cooldown in a model's availability; an xAI WebSocket resets its terminal error when it is configured again; an OpenAI-compatible stream's time to first token is measured on its first token frame; and the v8 config API normalizes collection styles and unquotes mapping keys.
- **Ported from CLIProxyAPI v8.0.20**, up from v8.0.15. What the move left out, and why, is in [UPSTREAM.md](UPSTREAM.md#what-moving-from-v8015-to-v8020-left-out). Besides the speech endpoints, it brings:
  - **`server.github-token`** (or `github-token` in the legacy layout), a token for requests to GitHub's API: the management API's latest-version check sends it ahead of `GITHUB_TOKEN`. The management API never shows it.
  - **Compact error bodies**: an upstream error body that is already JSON is compacted to one line, so a stream's `data:` line carries it whole.
  - **No more silently dropped attachments**: a file, audio or other part a provider can't take gets a 400 before anything is sent, and a turn left with nothing in it isn't sent.
  - **Credential manager fixes**: a credential whose access token the provider refused (401) stays out of rotation while it refreshes, without ending a model's quota cooldown; a call's outcome from before a credential's tokens changed no longer cools it or counts against it; and a refresh that started before the tokens were replaced doesn't put the old ones back. The management API's credential JSON shows `credential_version`.
  - **Claude**: `prompt_cache_options.mode: "explicit"` keeps only the client's own cache breakpoints, and `prompt_cache_options` is never sent to Claude.
  - **Translation fixes**: Claude document blocks for Gemini, Gemini's camelCase `systemInstruction`, refusal finish reasons and signed visible text for Claude clients, object types in Gemini schemas, a Codex web search's sources for Claude clients, encrypted reasoning of an unknown format kept in Codex compat mode, and a Responses stream that ends cleanly after its finish reason completed without `[DONE]`.
  - **Usage**: an answer whose `apply_patch` call fails keeps the usage it read, and a Vertex AI stream that ends after its last chunk counts as a success.
