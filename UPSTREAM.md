## Porting conventions

- **Port behaviour, not lines.** Upstream manipulates raw JSON with gjson/sjson. We use `serde_json::Value` so unknown fields pass through untouched, and typed structs only where they help.
- **Every ported file gets a header** naming its source, for example:

  ```rust
  // Ported from CLIProxyAPI internal/translator/codex/claude (v8.0.20, MIT).
  // https://github.com/router-for-me/CLIProxyAPI
  ```

- **Deviations are documented** in the file, with the reason (usually an upstream issue number).
- **Go means Go 1.26.** Upstream's releases are built with Go 1.26.4, so where its behaviour comes from Go's standard library we match Go 1.26, whatever version a ported file's header names. The difference shows in `encoding/json`, which from Go 1.27 runs on its v2 implementation, and in the Unicode tables: Go 1.26 has Unicode 15.0. Case mapping uses Rust's newer tables, so a letter added to Unicode since 15.0 may change case where upstream leaves it. Where upstream calls `strings.ToLower` or `ToUpper`, the port maps each character by its simple mapping as Go does (`open_ferry_translate::go::to_lower` and `to_upper`), not with `str::to_lowercase`, which differs for `İ`, a word-final `Σ` and `ß`. Where it calls `strings.EqualFold`, the port walks Go's case-folding orbits (`go::equal_fold`), so `ﬅ` and `ﬆ` differ though both upper-case to `ST`. Go's `json.Valid` allows 10,000 levels of nesting and gjson's `Valid` any; `go::json_valid` and `go::gjson_valid` follow whichever upstream calls.
- **Bugs we find upstream get reported upstream**, with a failing test case where we can.

### Deviations so far

Each ported file lists its deviations in its module docs. Most are byproducts of using `serde_json` rather than raw bytes:

- **Key order is kept.** Upstream round-trips tool schemas through Go maps, which sorts their keys. We keep the client's order (`serde_json` with `preserve_order`). In the Responses and Claude to Chat Completions requests we keep a schema's number text too, where upstream writes each number as a `float64` (`1.50` becomes `1.5`, and integers beyond 2^53 lose precision). In the Claude to Chat Completions request, a `properties` the schema is given is added last.
- **Embedded JSON is re-serialized compactly.** Where upstream copies a client's raw JSON bytes into a string field (for example `function_call.arguments`), we write the same value as compact JSON. A request body's numbers are kept exactly as written, `-0` and exponents included: the proxy reads the client's JSON keeping each number's text, and hands it to the translators that way. Elsewhere, in a response and in JSON most translators read out of a string, number text is kept as `serde_json` reads it (`arbitrary_precision`): digits, trailing zeros and integers of any length stay as written, but `-0` becomes `0` and an exponent is respelled with a small `e` and a sign (`1E20` becomes `1e+20`, `1e5` becomes `1e+5`). The Interactions translators keep each number as written there too, in the responses they read and in JSON they read out of a string, and so do the Codex responses translated for Claude and Gemini clients and the Chat Completions responses translated for Gemini clients, in a call's arguments. In responses this affects a web search's `partial_json`. Function call arguments are passed through byte for byte. In the Responses to Chat Completions request it also affects a custom tool call's `input` that isn't a string, which upstream copies as text into the call's `{"input": ...}` arguments, and a local `shell_call`'s `action` and a whole `shell_call_output` item, which upstream copies as text into a call's arguments and output. A Chat Completions call to the local shell translated for a Responses client gets its arguments as the `shell_call`'s `action`, compact and keeping each number's text, where upstream copies them as they came. In the Claude to Chat Completions request it affects a tool call's `arguments`, a tool result's content that isn't text, and a value read as text that isn't a string, such as a `stop_sequences` item or a `user` that is an object. In Chat Completions responses translated for Claude, Responses and Gemini clients, it affects values read as text that are objects or arrays, such as content, reasoning and tool call arguments. In requests from Gemini clients it affects call arguments, a function response written as text, and text, tool descriptions and stop sequences that aren't strings. The Chat Completions request derives the IDs of calls without one from that JSON, so they differ from upstream's when the client's JSON isn't compact; they are still the same for the same request. In the requests to Gemini, it affects values read as text that aren't strings (text, tool names, the reasoning effort, and a Gemini call's name given to the unnamed response that answers it), a tool result stored as text, and the type hints the schema cleaner writes into a description for a `type` that is an object or array. In Gemini responses translated for Claude and Chat Completions clients, it affects a function call's `args`.
- **An empty `reasoning` object is no reasoning however it's written.** The Responses to Chat Completions translator compares the object's text with `{}`, so upstream counts `{ }` as reasoning turned on and gives tool call turns the `[reasoning unavailable]` placeholder. We don't.
- **Strings use `serde_json`'s escaping.** Where upstream writes a string with Go's JSON encoder, it escapes `<`, `>`, `&`, U+2028 and U+2029 as `\u003c` and so on. We write them as they are; the JSON values are the same. The error bodies the server writes itself (`errors::openai_body`, `claude_error_json` and `local_error`) are escaped as Go's are.
- **Malformed JSON is not read.** A Codex `data:` line that isn't valid JSON is treated as an event with no fields, or gives no chunk in Chat Completions; gjson reads what it can from it. The same goes for a Claude `data:` line, for a Chat Completions `data:` line or response translated for Claude and Responses clients, and for a Gemini chunk or response translated for Claude and Chat Completions clients. gjson skips anything before the first `{` or `[`, which lets upstream's Gemini to Claude translator read the `data:` lines Vertex AI's executor passes it; ours reads from there too. `serde_json` also rejects an unpaired surrogate escape such as `\ud800`, which gjson reads as U+FFFD. Nor can `serde_json` read JSON nested more than 128 levels deep. A Claude `data:` line that is valid JSON but can't be read for one of these reasons, or because it isn't UTF-8, ends a Responses stream with `response.failed` when the request declares `apply_patch`, since it could carry part of a patch; otherwise it gives nothing. A whole Claude Messages response, which the Chat Completions and Responses translators read as the events that build it, is taken as such a line when it can't be read for these reasons, where upstream writes its events. A Chat Completions line or response does the same when translated for a Responses client, a whole response becoming the failed response. A Gemini chunk or response translated for a Responses client goes further when the request declares `apply_patch`: any chunk or response that can't be read, valid JSON or not, fails the stream or gives no response, where upstream fails only when it finds an `apply_patch` call in invalid JSON. Without `apply_patch`, such a Gemini response gives one with no output. Translated for a Claude client, a whole response whose tool call arguments can't be read gives the call an empty `input`, where upstream copies them. Providers don't send such lines, so this only matters for corrupted streams. Likewise, a Chat Completions tool message's string content is read as JSON parts only if all of it is valid JSON, and so is a Responses tool output's string when it is checked for images to send to Chat Completions. A Chat Completions call to a Responses client's local shell has a valid action only if `serde_json` reads its arguments, so commands holding an unpaired surrogate escape fail the response, where upstream reads U+FFFD.
- **Block order instead of Go map order.** Where upstream walks a Go map, whose order is random, and the output depends on it, we go in ascending order. When a Claude stream ends with tool calls still open, the Responses translator closes them in block order. A Chat Completions stream translated for a Gemini client gives its function calls in tool call index order.
- **Byte-length truncation keeps whole characters.** Upstream cuts names and IDs at 64 bytes and can split a UTF-8 character; we stop at the character boundary before it.
- **Duplicate object keys: the last one wins.** gjson reads the first occurrence of a key and `serde_json` keeps the last. RFC 8259 leaves this to the parser. For the same reason, a Gemini part with two `thoughtSignature` keys counts as normalized; upstream re-sanitizes it, and a local shell call's arguments are checked, and kept as its action, by the last of a key given twice, where upstream checks the first `commands` but every key and keeps both.
- **Out-of-range numbers saturate.** Where upstream converts a float such as `1e30` to an integer, Go's result depends on the CPU: amd64 gives the minimum int64, arm64 saturates. We saturate, so a huge thinking budget maps to the highest effort, and a token count of `1e400` becomes the largest int64.
- **Numbers beyond `f64` are kept as written.** Where upstream copies a value as a number, such as Chat Completions' `reasoning_effort`, Go writes `1e400` as `+Inf`, which isn't JSON. We keep the number's text. Where upstream converts the value to a float first, as for a Claude request's `top_p`, a Claude request's `temperature` and `top_p` sent to Chat Completions, a Gemini request's `topP` sent to Claude, its `temperature` and `topP` sent to Chat Completions, the sampling settings of Claude and Chat Completions requests sent to Gemini and the latter's token limits, or a legacy Completions request's `temperature`, we leave out a value that isn't finite. Reading Chat Completions tool call arguments leniently for a Gemini client, a number Go reads as infinite or NaN, such as `inf`, stays text. Where Go's `json.Marshal` meets such a number, as in a Completions choice's `logprobs`, it fails and upstream writes the field with no value; we keep the number. A Responses result that repeats such a `temperature` or `top_p` from the request gets `null`. In the Responses to Chat Completions request, such a number in `text.format` or in a tool's parameter schema is kept as written; upstream writes `+Inf`, or fails to write the request when the number is inside an object or array. In the Claude to Chat Completions request, such a number in a tool's `input_schema` is kept as written; upstream fails to write the tool.
- **No made-up user IDs.** When a Chat Completions, Responses or Gemini client sends no user ID, upstream fills the Claude request's `metadata.user_id` with a hash of the conversation. We pass on only an ID the client sent, in `metadata.user_id` or `user`, and otherwise send empty `metadata` (see [Deliberately not ported](#deliberately-not-ported)).
- **Gemini `createTime` is in UTC.** Upstream writes a Gemini response's `createTime` in the server's time zone: the time of a Codex response's `created_at`, or the current time for a Claude response. We write the same instant in UTC.
- **Tool arguments that aren't JSON become `{}`.** For a Gemini client, upstream copies a Codex call's arguments that start with `{` but don't parse, and a Claude tool call's input that doesn't parse, into the function call's `args` as they are, so the response isn't JSON. We give the call empty `args`.
- **Schema types are lowercased wherever they are.** Sending a Gemini request's tools to Codex, upstream finds each `type` by gjson path, so it misses one under a key holding path syntax such as `#` or `|`; we lowercase them all. Sending them to Claude, upstream sets a lowercased `type` by sjson path, which can pad an array with any number of nulls or corrupt the JSON when a value on the way is text; we pad with at most 1,024 and build the array sjson's rules describe. That path reads syntax other than `.`, `*` and `?` in a key, such as `|`, `@`, `\` or a leading `:`, so upstream may leave that `type` alone or lowercase another key's, adding it if it's missing; we lowercase the `type` under the key as written.
- **Generated tool call IDs come from a keyed hasher.** A Chat Completions or Responses tool call without an ID gets one in upstream's form, `toolu_` and 24 letters and digits. Upstream draws them from the operating system's random source; we draw them from the standard library's randomly keyed hasher, so the crate needs no random-number dependency. The IDs only need to be unique within a conversation.
- **Registry response streams are objects.** Upstream's registry passes each response chunk with a `*any` that the translator fills on the first call. Ours makes a `ResponseStream` per response, which looks up the translator once and holds its state. It leaves out empty chunks, which upstream's stream manager drops before its handlers see them: its Codex to Claude translator returns one, possibly empty, for each `data:` line, and its Chat Completions passthrough one for each line but `[DONE]`.
- **The translators read the static model catalog.** Whether a Claude model takes adaptive thinking or a token budget comes from upstream's model registry, which holds the models of configured accounts and falls back to a static catalog. The translators read the static catalog in use, the built-in one or the one read from the file `models.catalog` names, as upstream's registry holds the catalog its updater loaded; the Claude executor reads the registry. The Responses to Gemini translator also reads the static catalog for whether a model takes Gemini's web search tool; upstream asks its registry, then the catalog, and also whether an Antigravity account has found that the model takes it, which never happens here.
- **A `null` client request counts as missing.** The Responses response translators for Claude and Chat Completions upstreams read the tools and the repeated fields from the client's request, else the translated one. A client's request that is JSON `null` counts as missing here; upstream takes it. The server routes no such request, since it names no model.
- **Escaped cache breakpoint keys are removed too.** Upstream strips `prompt_cache_breakpoint` from Responses `input` only when the body holds the key unescaped. We strip it however it's written.
- **The signature sanitizer's default target falls back to the model.** `ClaudeMessagesSanitizeOptions::default()` targets `Provider::Unknown`, which falls back to the target model's provider. Upstream's zero value is an empty provider, which skips that fallback.
- **The Responses to Claude translator logs no warnings.** Upstream's logs a warning when it drops input items of a type it can't convert, and when a history still breaks Claude's tool pairing rules after its repair. We drop the same items and make the same repairs, without the warnings: the translators are plain functions with nothing to log with.
- **Protobuf errors always use a regular space.** Signature errors include protobuf-go's parse errors, which start with `proto:` and a space. protobuf-go makes that space a non-breaking one in some builds, chosen per binary so that callers don't compare error strings. We always write a regular space.
- **A Q-form Claude signature is checked after one cache prefix.** Upstream's Claude validators strip a signature's cache prefix, up to the first `#`, then pass an Antigravity Q-form signature to the Q check, which strips up to a `#` again. So `x#Qjunk#Q…`, with a valid Q signature after the second `#`, passes as `Qjunk#Q…`, which isn't a valid signature, and normalizing it returns that text. We check what is left after the first prefix, so it fails. Replay decisions treat a signature with a second `#` as unknown either way.
- **Not ported in `signature`:** upstream's debug logging when it sanitizes Gemini signatures. Its tests of that logging are not ported, nor are tests that read captured signature corpora, which aren't in its repository.
- **The `apply_patch` bridge belongs to the executor.** Upstream's Codex to Responses response translator takes the bridge in its state parameter, but only its tests pass one; its xAI, Meta and Kimi executors run their events through `ApplyPatchResponsesState` before translating, and its Codex executor never turns the bridge on. Ours is the same: an executor builds an `apply_patch_responses::State` (or a translator `Bridge`, for `translate_line_with_bridge`) and passes the events through it. The Meta and xAI executors do. The bridge writes an event it changes, even one it only renumbers, as compact JSON, where upstream edits the event's text; an event that isn't JSON passes through it unchanged, and one that is valid JSON but can't be read, such as one nested too deeply, fails the stream. An `input`, `output` or tool choice `tools` that isn't an array is read as empty by the translator's bridge.
- **The `apply_patch` dispatcher's buffering is bounded.** Upstream's `ApplyPatchResponsesState` keeps every event of a call that may be to a namespace dispatcher, and the provider's text of it, until the response ends, so a stream that never completes a call grows it without end, whatever the limit on a line. Ours counts what it holds for those calls: the bytes of their events, snapshots, streamed arguments and keys, the events and snapshots themselves, and the calls. It fails the response once any passes its limit: 200 MiB (four times the Codex stream's 50 MiB line limit, so that a line of the largest size fits in all three places an event is kept), 262,144 events (twice a 128K-token call's, one delta each), or 16,384 calls. The failure is the one a conflict gives, one `response.failed` event and an error, at the event that passes the limit. `remember_dispatcher_event` and `remember_dispatcher_arguments` can't report an error, so past a limit they stop keeping what they're given, and the failure comes at the next event or the end of the stream. Under the limits the output is upstream's.
- **OpenAI-compatible upstreams get open-ferry's user agent.** Requests to them say `User-Agent: open-ferry/<version>`, unless the client sent its own, where upstream always sends `cli-proxy-openai-compat`; an entry's `headers` can't set `User-Agent` or another header that says which client is calling. No `prompt_cache_key` is made up: one the client sends still reaches a provider with `support-prompt-cache-key`, but upstream's keys derived from a Claude Code prompt or a session aren't sent.
- **Gemini and Vertex AI get open-ferry's user agent.** Requests to them say `User-Agent: open-ferry/<version>`, unless the client sent its own, where upstream sends Go's default; no `x-goog-api-client` or other header of Google's own client libraries is sent, and a credential's `header:x-goog-api-client` attribute is dropped. A Vertex AI service account's token is cached per account until shortly before it expires, where upstream fetches one for every request, and only `service_account` credentials are taken.
- **A credential's custom headers can't name any vendor's client.** Upstream applies every `header:` attribute. Here one that says which client is calling is dropped with a warning that names the header, whether its value is a literal or a `$Name` taken from the client's request: `User-Agent`, `X-App`, any `X-Stainless-*`, `Originator`, the session, conversation, thread, window, agent and container IDs, and the vendors' own, `X-Goog-Api-Client` (Google's API client), `X-Client-Id` (Meta's), `X-Xai-Token-Auth` (xAI's client token), any `X-Msh-*` (Kimi's platform, version and device) and any `X-Grok-Client-*` (xAI's client version and identifier), in any case. This holds for every executor and for a credential's quota probe, and is stricter than upstream, where a credential can set any of them and pass for another client. A header that merely looks like one (`X-Goog-Api-Key`, `X-Goog-User-Project`, `X-Client`, `X-Mshx-Version`) is applied.
- **File credentials follow a reload without being read again.** On a reload, each file credential's excluded models are worked out again from the credential as registered and the new `oauth-excluded-models`, keeping its tokens and state. Upstream synthesizes every auth file again and updates the credentials that differ, so a change to a file that the watcher has yet to report is applied then, rather than with the report.
- **OpenAI-compatible executors follow the config, not every reload.** They are made again only when `proxy-url` or `openai-compatibility` changes, and one that no credential uses any more is unregistered; upstream makes every executor again on each reload and keeps them. A credential of a provider this port has no executor for isn't served, where upstream hands it to an OpenAI-compatible executor.
- **The native executors are made again only when the config changes.** The Codex, Meta and xAI executors are made again on any change, which ends their WebSocket sessions as upstream's every reload does, so each setting they read takes effect with the next request. The other native executors are made again when `proxy-url`, `claude.model-level-cooling`, `codex.orphan-delegation-compatibility` or `client.codex.optimize-multi-agent-v2` changes. Upstream makes every executor again on each reload.
- **Model catalog sources are files.** `models.catalog` and `models.codex-catalog` are read when they name an absolute path, and followed as the file changes (see the model registry row). An empty source is the built-in catalog, where upstream downloads one from its own URLs unless `-local-model` is given. A URL source isn't fetched: the load or reload that sets it logs a warning naming the setting, and the catalog in use stays. `models.devin-catalog` is checked but not read. A file is read before the start or the reload returns, where upstream reads it in the background and registers the credentials' models again once it has; it is also read when its size or modification time changes, checked every two seconds, where upstream reads it every three hours only. The warnings name the setting and say why a catalog was refused; upstream's say neither. The sources are checked as upstream checks them: one that is neither an http(s) URL nor an absolute path fails the load, and a reload to it keeps the config there is. With two bad sources, the error names the first of `catalog`, `codex-catalog` and `devin-catalog`, where upstream's names one at random. The v8 config reads show the section as upstream's do.
- **The non-streaming response expects a complete final event.** Codex's `response.completed` often has an empty `output`. The Codex executor fills it with the streamed items before calling the translator, as upstream's does.
- **Codex reasoning replay only uses sessions the client named, in this process.** Upstream falls back to a session made from a UUIDv5 of the client's proxy API key, which a Claude client, the only kind replayed, never reaches; we make none. Home mode's shared store isn't ported, so the cache is the process's own and reading or clearing it can't fail a request. A turn's fingerprints hash each item's JSON as `serde_json` writes it, where upstream hashes the bytes as they came; they are only compared with fingerprints made the same way. A payload or Codex turn metadata that isn't valid JSON names no session. Entries are keyed by a SHA-256 hash of the model and session, each with its length, so a long session key takes no more room than a short one and a NUL can't make two pairs share an entry. A `%` or `:` in a Claude Code session or agent is percent-encoded in its scope: upstream's scope for session `s:agent:a` and agent `main` is also its scope for session `s` and agent `a:agent:main`, so one could be given the other's replayed reasoning and tool calls.
- **Provider errors don't repeat a secret the request sent.** An upstream's error body, or an error in its stream, reaches the client as the error's message. Where it quotes a secret the request was sent with, as it is or escaped as JSON, the Codex (HTTP and WebSocket), xAI (HTTP and WebSocket), Claude, OpenAI-compatible, Gemini, Vertex AI and Meta executors replace it with `[redacted]`; upstream passes it on. Only those forms are recognised: a secret written any other way, with other escapes, in another encoding, or split across lines or messages, is left as it is. The secrets are read from the request as it was finally sent: its credential headers after the custom ones (the API key or token among them), each cookie value, the credentials in its URL (the user info's password, the `Basic` credential made of it and the query values that hold a secret, see [Log files and config changes](#log-files-and-config-changes)), its proxy's password and the `Proxy-Authorization` credential made of it, and the credential's own keys and tokens. A proxy's refusal, such as a 407, and the text of a failure to connect are scrubbed the same way. The Gemini, Vertex AI, Claude, Codex, OpenAI-compatible, Meta and xAI streams have them replaced on every line, or on every message over the Codex and xAI Responses WebSockets, an error's or not (with, for a call that keeps a connection, the secrets that connection's handshake sent as well), and what a model says in a successful answer is redacted too (see the next point). The Codex Alpha Search pass-through, and xAI's plain HTTP requests, redact them from the body of every answer, whatever its status, which upstream hands on as it came. Only a secret of eight bytes or more is replaced, as in every client error (see `Policy::Client`); a shorter one is left alone, since it could be an ordinary word. What is written to disk or served to the management API, such as a usage record or a request log, is scrubbed of a secret of any length (see `Policy::Disk`).
- **Provider requests follow redirects only within their origin.** The Codex, Claude, OpenAI-compatible, Gemini and Vertex AI executors, their logins and token refreshes, and the Vertex AI token exchange follow a redirect only to the scheme, host and port of the first request, and at most nine, as Go's client does; a redirect to another origin comes back as the answer, an error with its 3xx status. Upstream follows a redirect anywhere, and Go's client then drops only `Authorization` and cookies: `x-goog-api-key`, `x-api-key` and other headers go along, and a 307 or 308 sends the body again, such as a service account's signed assertion.
- **Answers that succeed have the request's secrets redacted too.** The secrets that an error is redacted of (see "Provider errors don't repeat a secret the request sent") are replaced with `[redacted]` in what a model says in a successful answer, so a model that says the API key, token or cookie it was sent doesn't hand it to the client, and in a 200 whose body holds an `error` object that quotes one; upstream passes the answer on as it came. A body that isn't streamed is read whole, redacted, and only then translated: Gemini and Vertex AI `generateContent` and `countTokens` calls (up to 50 MiB) and Interactions calls, translated for the client or not, a `failed` interaction included; Claude messages and token counts; OpenAI-compatible completions and compact answers; Codex and xAI compact answers, and the events an xAI `compaction_trigger` gets, made from one; and Meta answers. A stream is redacted line by line, before the line is read: the Gemini, Vertex AI, Interactions, Claude, Codex (over HTTP), OpenAI-compatible, Meta and xAI (over HTTP) streams, and the one a call that isn't streamed reads. Over the Codex and xAI Responses WebSockets, each message is redacted before it is read, a streamed call's or not. The call's taps, which feed the usage records and the request log, read the answer as it came; the log scrubs it of every secret itself (see "More is kept out of the files").
- **Secrets stay out of logs and `Debug` output.** The Codex and xAI WebSocket log lines hide every secret the connection or call sent, however short, from each field they fill in: the session, the credential's ID, the URL, the event type and the IDs xAI or the client sent, and the failure; so does the line for an xAI `compaction_trigger`. Upstream logs them as they are. A failed Vertex AI token exchange is logged with the endpoint's OAuth `error` and `error_description`, but with the signature of the assertion it was sent redacted, since the assertion grants a token until it expires; upstream logs the description as it came. The `Debug` output of a config entry, a synthesized credential's entry and a registration entry shows a base URL without its user info, query and fragment, and no proxy URL. An auth file the watcher reports shows its path and the length of its contents, and a management response body its kinds, keys and lengths, never a string or a number.
- **OpenAI-compatible streams are bounded.** A frame's `data:` lines, joined, may hold at most 50 MiB, as one line may; a bigger frame ends the stream with a 502, `upstream SSE data frame is too large`. Upstream holds any amount.
- **OpenAI-compatible base URLs are read as WHATWG URLs.** Their `.` and `..` segments are resolved, where Go sends them as written. A base URL with an ASCII control character fails before anything is sent, as in Go, with Go's message but without the URL, which may hold a secret. As with Go's HTTP client, a custom `Content-Length`, `Transfer-Encoding` or `Trailer` header is ignored.
- **Codex Alpha Search URLs are read as WHATWG URLs.** An API key's `base-url` plus `/alpha/search` has its `.` and `..` segments resolved, percent-encoded ones such as `%2e%2e` included, and a `\` read as `/`, where Go sends `/v1/%2e%2e/alpha/search` as written and a `\` as `%5C`. A URL with an ASCII control character fails with 502 before anything is sent, as in Go, with Go's message but without the URL, which may hold a secret.
- **Codex Responses URLs are read as WHATWG URLs.** A credential's `base_url` plus `/responses` or `/responses/compact`, over HTTP or the Responses WebSocket, has its `.` and `..` segments resolved, percent-encoded ones such as `%2e%2e` included, and a `\` read as `/`, where Go and gorilla send `/a/%2e%2e/codex/responses` as written and a `\` as `%5C`. A URL with an ASCII control character before any `#` (for the WebSocket, once trimmed) fails before anything is sent, as in Go, with Go's message (`net/url: invalid control character in URL`) but without the URL, which may hold a secret, and with no status, as Go's error has none.
- **The Codex client model list decides `apply_patch` by provider name.** Upstream gives a model `apply_patch_tool_type: "freeform"` when the executor of every provider serving it says it takes the tool. We go by the provider's name (`codex`, `claude`, `xai`, `gemini`, `gemini-interactions`, `vertex`, `meta`, `openai-compatibility` or `openai-compatible-<name>`), so executors need no new method. The list is built from the models sorted by ID, where upstream's order varies and decides the order of models with the same priority, and `client_version=cpa` gets no `cpa_capabilities`.
- **Chat Completions tool call arguments that aren't JSON are left out.** Upstream copies a tool call's `function.arguments` into the Gemini request's `args` as raw JSON, so arguments such as `""`, or missing ones, make the request invalid JSON. We send the call without `args`.
- **In the Responses to Gemini translator:** a function call's `arguments` that start like a JSON object or array but aren't valid JSON go to Gemini as the text `args.arguments`, where upstream copies them as they are and makes the request invalid JSON. A value read as text that isn't a string, such as a text part's `text`, the `instructions` or a tool output that answers no call and is neither a string nor a list, is written as compact JSON, where upstream copies the client's JSON text. A remote file's URL is checked as Go's `url.Parse` checks it, except that an IPv6 host in brackets is checked with Rust's parser. Grounding chunks without a URL are told apart by their compact JSON, not the text Gemini sent. A stream reads the request's tool declarations, the fields its final event repeats and the query a search falls back to once, when it starts. The reasoning replay cache keeps only its in-process store, without Home, snapshots, revisions or branches, which the translator doesn't use; it purges expired entries on the first call 10 minutes after the last, not from a background task, and measures an entry by serde_json's text. A read that finds nothing leaves no marker behind, and entries are keyed by a SHA-256 hash of the model and session, each with its length, so a client can't fill the cache with session IDs of its choosing. `isTrailingOpenAIResponsesAssistantPrefill`, `HasOnlyResponsesWebSearchTools` and `mapByteOffsetsToRuneRange` are not ported: nothing calls them.
- **The Interactions translators share the deviations above.** In all five families (Claude ↔ Interactions, Chat Completions ↔ Interactions, Responses ↔ Interactions, Gemini ↔ Interactions and Interactions → Codex), malformed JSON is not read, embedded JSON and a value given where text belongs are written as compact JSON (such as a call's `arguments` object, whose text upstream copies), with each number as written, the last of a repeated key counts, where gjson reads the first, and out-of-range token counts, indexes, thinking budgets and times saturate. A model whose name contains `antigravity` is translated like any other: upstream's `isAntigravityModel` branches in the Chat Completions and Responses families are not ported, which rename the tools whose names clash with Antigravity's own to `external_` names and back (`AntigravityToolNameToUpstream` and `AntigravityUpstreamToolNameToClient`, in tools, tool choices, calls and results), move the token limit to `agent_config.max_total_tokens` in place of the sampling settings, and keep the `automation_update` tool. Each family also has its own:
  - **Responses ↔ Interactions.** Tool descriptions go on as the client wrote them: for every model but an Antigravity one, upstream's request translator rewrites the wording of two well-known ones (`SanitizeDevinToolDescription`), which only disguises the client. The `automation_update` tool of the `mcp__codex_app` namespace is still left out, and so is a `tool_choice` that names it, as upstream does. A call's `arguments`, or an output's `output` or `result`, that is a string of JSON `serde_json` can't read (nested over 128 levels, or with an unpaired surrogate escape) goes on as a string, where upstream embeds it. A `temperature`, `top_p`, `presence_penalty` or `frequency_penalty` that isn't a finite number is left out, where upstream writes `+Inf` or `NaN`, which isn't JSON. The response translators read malformed JSON up to its first error. A whole Interactions response's `output` holds the items at the indexes its steps used, where upstream also looks up every index below the largest, which finds nothing more.
  - **Claude ↔ Interactions.** Upstream's stream from Claude to Interactions leaves out a `tool_use` block's streamed `input` when its JSON text is exactly `{}`; we leave out any empty object, however it's spaced, since we don't see the text.
  - **Gemini ↔ Interactions.** JSON upstream copies as text is written compact: the arguments of a stream's `arguments_delta`, a function result holding a `$ref`, which is stored as a string, and an object where a string is wanted (a `thinking_level`, a text, a signature or a description). Arguments or a result given as a string that gjson finds valid but `serde_json` can't read stay `{}`, or the string, where upstream copies the text. A generation config key holding `|`, `#`, `@`, `*` or `?` is left out, where upstream's sjson reads a query, and so is a digit key that would pad an array with more than 65,535 nulls or index into an array it doesn't reach, where upstream runs out of memory or panics. A key with a character other than ASCII just after an `_` is written once, with all its leaves; upstream's camelCase cuts that character in two, so sjson never finds the key it wrote and writes it again for each leaf, and a reader that keeps the last duplicate gets only the last leaf. A generation config leaf whose path sjson reads as more than 128 keys (a key of many dots, say) is left out, where upstream nests a value for each key, however many: 5,000 dots make 5,000 nested objects.
  - **Interactions → Codex.** The generation config's settings are copied to the request in the order upstream lists them, where upstream walks a Go map, so when two set the same field (`max_tokens` and `maxOutputTokens`, say) the last listed wins and `verbosity` lands within a copied `text`, where upstream's result changes from run to run. A tool name cut to 64 bytes is cut at a character boundary, where upstream can split a character. A Codex event or body that isn't valid JSON reads as one with no fields, where gjson reads what it can. A call's `arguments` that start as a JSON object but aren't one are written `{}`, where upstream writes them in as they are and its response isn't JSON. A client's own `prompt_cache_key` is not passed on: upstream's translator doesn't copy it, and the port keeps to that.
- **The Gemini Interactions executor runs no plugin hooks.** Upstream translates an Interactions call's request (`translateGeminiInteractionsRequestPair`) through `sdk/translator`'s plugin hooks (`SetPluginHooks`), once for each distinct input. The registry has no plugin hooks, so the built-in translators alone translate it. `is-compat` isn't read for its API keys: a request is translated as for a model that isn't a compatibility model. A call handed to the Gemini executor is recorded as `gemini`'s, where upstream names it `gemini-interactions`.
- **The Gemini schema cleaner takes path syntax in keys literally.** Upstream's cleaner builds gjson paths from schema keys without escaping `|`, `#`, `@` or a leading `[`, `{`, `!` or `:`, so its edits through such a key resolve as queries or not at all. We edit the key itself. It also drops nullable properties from `required` in document order, where upstream walks a Go map.
- **The Gemini schema cleaner's output is bounded.** Where it writes a `$ref`, `type` or description that is an object or array into a hint or a type, it writes at most the first 1,024 bytes of its JSON; upstream writes all of it, so values nested in one another double the text at each level, and a 600-byte schema can come out as 16 MB. Merging `if`/`then`/`else` branches copies at most 65,536 more values than the schema holds, after which the remaining, shallower branches add nothing to their parents; upstream's copies double with each level of conditionals nested in a branch. For the same output, it also removes the keys an object loses at once and appends to a `required` list, where upstream rewrites the object once per key and the list once per `allOf` branch that adds to it, which takes time quadratic in their size.
- **Thinking settings use the model the registry has.** Upstream's API-key executors apply a request's thinking setting for the model definition the credential manager bound to the credential (`ResolvedModelInfo`), and then map an `xhigh` or `max` level onto that model's levels. That binding isn't ported, so the Codex and OpenAI-compatible executors look the model up under their provider in the model registry, else in the built-in catalog, as upstream does when nothing is bound. The parity suites run upstream's `ApplyThinkingWithModelInfo` with the model bound, through `apply_with_model_info`, which reads a Responses client's request that isn't valid JSON as having no effort where gjson reads what it can. A plugin's request normalizer isn't ported either, so a Responses client's effort updates are always read from its request.
- **Codex multi-agent v2 tools are prepared twice.** Upstream's Responses handler notes in the Gin context that it prepared a Codex client's tools, and the Codex executor then leaves the `spawn_agent` model list alone. Nothing keeps that note here, so the executor writes the list again: the same one, unless the models changed in between, when the newer list wins. The list isn't cached by catalog revision and registry generation either; it is made again for each request with a `spawn_agent` tool.
- **An orphan delegation output that isn't a string is quoted as compact JSON.** Upstream quotes it as the client wrote it.
- **Restoring the collaboration namespace stops at 128 levels.** Upstream re-encodes an upstream event it renamed with Go's `json.Marshal`, keys sorted and `<`, `>`, `&`, U+2028 and U+2029 escaped, and so do we, but data nested more than 128 deep is left as it is, where Go reads up to 10,000, so the recursion can't overflow the stack.
- **The Codex Responses WebSocket handshake sends nothing made up.** It sends the credential's token, `OpenAI-Beta: responses_websockets=2026-02-06` (or the client's own value if it names `responses_websockets=`), a ChatGPT credential's own `ChatGPT-Account-ID`, the credential's configured headers (which can't set `User-Agent`, `Originator`, a session, conversation, thread or window ID such as `Session_id`, `Conversation_id`, `Thread-Id` or `X-Codex-Window-Id`, or another client identity header, as for HTTP), and the client's own `x-codex-beta-features`, `x-codex-turn-state`, `x-codex-turn-metadata`, `x-client-request-id`, `x-responsesapi-include-timing-metrics`, `Version`, `Originator`, session ID (as `session_id`) and, for a native client, `X-OpenAI-Internal-Codex-Responses-Lite`. `User-Agent` is the client's, else `open-ferry/<version>`. Upstream's fallbacks aren't sent: the `codex-tui` `User-Agent` and `Originator`, `codex_cli_rs`, `codex-header-defaults`' user agent and beta features, a `session_id` made up for a `Mac OS` user agent, `session_id` and `Conversation_id` from a prompt cache key, a `prompt_cache_key` from the Claude Code prompt cache or a provider session, cloaking headers, and the routing hint. Neither `Content-Type` nor `Accept` is sent, as upstream sends neither.
- **Codex Responses WebSocket connections are the executor's and close sooner.** Each Codex executor keeps its own sessions, where upstream's store is global. A connection is reused only for the same credential, URL, proxy and token, so a refreshed token connects again where upstream keeps the connection. A connection that ends, with its session, on idling or for a new token, is closed before its call is handed the failure, and closing a session ends its call once the call has read what its channel holds, where upstream's reader waits for the call to make room for the failure. A closed session stays closed, so a handshake under way is abandoned and a connection that comes up anyway is closed unused, where upstream gives the closed session the connection and sends the request on it. A call dropped before it ends closes its connection, so the rest of its response can't reach the session's next call; upstream leaves it open. A message or frame may be at most 50 MiB and the handshake's response head 64 KiB, where gorilla has no limits; `permessage-deflate` isn't offered. A SOCKS5 proxy is refused with a 502, as `api-call` refuses it, where upstream dials through it; `CONNECT` says `User-Agent: open-ferry/<version>`. Only a Responses WebSocket client takes this route, so its events reach the client as they are; upstream's translation for other clients isn't ported. An error event's body, a close reason, a refused handshake's body and any other failure to connect, such as a refused `CONNECT`, have the credential's secret redacted if it is of eight bytes or more, as in every client error (see `Policy::Client`), in the call's error and in the logs, where upstream passes them on; so has each message Codex sends, what a model says in a successful answer included, before it is read (see "Answers that succeed have the request's secrets redacted too"), while the call's taps read it as it came. A call that keeps a connection redacts the secrets that connection's handshake sent as well as its own, from Codex's messages and from its errors, as a credential's custom header may have changed since the connection opened: the connection is kept for the same credential, URL, proxy and token, whatever the headers. A status above 65535 becomes 500.
- **Codex response steering bounds what waits on Codex.** With `codex.response-steering` on, a Codex stream that keeps its connection for the client's socket (`codex::websocket::duplex`) ends with a connection error once more than 64 steering messages wait on Codex (sent and not yet answered, or accepted and not yet followed); upstream keeps any number, so a client could grow them without bound. One task reads Codex and the client and writes to Codex, where upstream runs a writer and a reader goroutine. The call's taps are told the first request, then each message read, where upstream records each later request and each response's usage. A frame that isn't UTF-8, or that `serde_json` can't read, gets the invalid JSON error; Go's `json.Valid` may take one. The client going away ends the stream with no error, where upstream's ends with `context.Canceled`, which its handler drops. Each message has the call's secrets redacted before it is read, as on any Codex WebSocket stream, and an empty one is skipped. The client's frames and the credential check travel in the call's options rather than its context. On the server (`handlers::responses_ws`), the task that reads the client's socket stops when the client goes or the socket closes, where upstream's also stops when the socket's context ends, and a client that goes away ends the turn under way at once, as upstream's socket context does; without steering it is noticed when a read, write or ping fails.
- **Compatibility models are resolved again.** Whether a `codex-api-key` model is `is-compat` is resolved from the config and the call's route model, as the credential manager would have bound it, where upstream reads what the manager bound to the call; a call the manager didn't make, and a token count it resolved nothing for, read the credential's entry. The other executors don't resolve the flag, so they take the path upstream takes for models that aren't compatibility models.
- **Codex image calls make up no client identity.** A call to Codex's Image API sends `open-ferry/<version>` as its `User-Agent` and the client's own `Originator`, if it sent one; upstream drops the client's `User-Agent` too, but its cloaking, on by default, then makes the call pass for `codex-tui`. Neither way makes up a `prompt_cache_key` or `Session-Id`, and models' `override_header` isn't ported. A form edit's fields are read in name order, a field's name is its JSON path as written without sjson's other path syntax, and its images replace an `images` field that isn't an array (sjson adds them to an object under the key `-1`). A JSON body that changes is written compact. The Image API's stream is passed on a line at a time, and its answer read up to 50 MiB; a tool call's answer is read a line at a time, up to 50 MiB a line, where upstream reads it whole, so a completed event read before the connection fails is answered. Every answer and error has the request's secrets redacted.
- **Codex Alpha Search makes up no client identity.** Upstream sends `Originator: codex_cli_rs` with every search; we send no `Originator`, not even a client's own. A search carries the credential's token, `Content-Type` and `Accept: application/json`, the credential's own `account_id` as `ChatGPT-Account-ID`, the client's own `Version`, `User-Agent`, `Session_id` and `X-Client-Request-Id`, and the credential's custom headers, which can't set an identity header; a client that sends no `User-Agent` gets `open-ferry/<version>`, where upstream's is Go's default. A payload over 16 MiB gets the proxy's usual 413, where upstream sends its first 16 MiB on. An answer without a `Content-Type` goes back without one, where Go's server sniffs one. A payload that changes has its top-level keys sorted and `<`, `>`, `&`, U+2028 and U+2029 escaped, as Go writes it, but its nested values are written as `serde_json` writes them. The route model is the payload's `model` as Go's decoder reads it into upstream's routing struct: the last string under any case of `model`, repeated keys included. A payload `serde_json` can't read, though Go's decoder can (with invalid UTF-8, a lone surrogate escape, or nested more than 128 deep), goes out as it came, with its Responses fields and its model as the client wrote them; its `model` still picks the credential.
- **Meta names no client of Meta's.** Upstream sends `X-Client-Id: tbh:tui` and a `User-Agent` of the form `muse-build/...` with every Meta request, and mints its key through Dynamic Client Assertion (`dca:` tokens). We send none of that: a request carries `Authorization: Bearer`, `Content-Type`, `Accept: text/event-stream`, `Cache-Control: no-cache`, the credential's custom headers and `User-Agent`, the client's own or `open-ferry/<version>`. A credential's `X-Client-Id` header is dropped, as every executor's custom headers drop it (see the custom headers bullet above), its `User-Agent` is ignored, and a `dca:` token is never sent as a bearer (a credential holding only one fails with 401 before anything is sent). Meta's sign-in, token mint and refresh, `PrepareRequest`, `HttpRequest`, `PrepareRequestAuth` and the typed token storage are not ported: a credential holds an API key (`api_key`) or an access token (`access_token`), and `refresh` returns it as it is.
- **The Meta executor differs from upstream's in small ways.** `is-compat` isn't read. A call with no token fails with one 401 message (`meta executor: missing API key or access token`); upstream has several, for the DCA and config-key cases. Error bodies are read up to 4 MiB, and an error body or event that quotes a secret the request sent has it replaced with `[redacted]`, if the secret is of eight bytes or more, as every client error is (see `Policy::Client`); so has what a model says in a successful answer, a non-stream answer whole and a stream line by line (see "Answers that succeed have the request's secrets redacted too"). A stream's usage, the served model and the response log are the taps' work, not the reporter's: the usage tap reads Meta's events as Codex's Responses usage and records the call as `MetaExecutor`. A `data:` line that isn't JSON is read as an event with no fields. The events of the `apply_patch` bridge are written as compact JSON. A dropped stream stops at once. The URL is read as a WHATWG URL, as for Codex.
- **A request nested 128 or more levels deep is refused.** Upstream forwards a request body of any depth, and its translators read it with gjson, which has no limit. `serde_json` reads at most 127 levels of arrays and objects inside one another, so a deeper body would be read as an empty one, with its model, messages and tools silently dropped before the call. Every route that takes a model's request (Chat Completions, Completions, Responses and its compact form over HTTP, each `response.create` and `response.append` on the Responses WebSocket, Claude Messages and `count_tokens`, Gemini `generateContent`, `streamGenerateContent` and `countTokens`, and Interactions for a model or an `agent`) answers a body of valid JSON that deep with a 400 `invalid_request_error` in its own error format, saying how deep the limit is, before any translator or executor sees it. On the WebSocket the error event goes out before the request is answered or kept, so the session is as it was. The depth is counted by a scan that keeps its nesting on the heap, so a body of any size is safe to check, and every array or object counts, the empty ones too. A body that isn't JSON isn't refused for its depth; the route answers it as it does any other. A body at the limit is converted as before, so a request that a translator makes deeper than the limit is refused when it is called.
- **A call's quota headers come with its result.** The credential manager keeps the quota headers of each Claude and Codex response, as upstream does, but reads them from the call's result, where upstream's `MarkResult` reads them from a holder in the request's context. A stream's are its headers, with those of the error that ended it over them, as upstream merges an error's into the holder. Devin isn't observed, as it isn't ported, so a `devin` result clears a snapshot that upstream would keep. Codex's `codex.rate_limits` WebSocket events aren't observed: upstream's executor merges each into the call's headers (`ParseCodexQuotaEventHeaders`), and here a WebSocket call is observed by its stream's headers alone. A header value's bytes that aren't UTF-8 are kept as U+FFFD, one for each byte, as Go's JSON encoder writes them.
- **A credential manager change is in use before it is saved.** A registration, an update or a refresh's result is published at once, then saved to the auth store with the manager's lock released, each credential's saves still in order. Upstream saves a copy first, with its lock released, merges back what the store changed in the copy (`mergeAuthSaveDelta`), and only then publishes. Our store gets a copy it can't change, so there is nothing to merge back. A reload of the store waits for the changes being saved, and changes wait for a reload, as with upstream's reload barrier, but neither wait can be given up, as upstream's contexts allow. There are no per-credential locks: each change is made whole under the manager's lock.

### Session affinity

With `routing.session-affinity` on, a conversation stays on the credential that served it, so its prompt cache stays warm (`manager::affinity`, from `SessionAffinitySelector` in `sdk/cliproxy/auth/selector.go` and `session_cache.go`, and `session`, from `sdk/cliproxy/session`):

- **Which session a call belongs to.** The one the client names: the session headers or body fields of Claude Code, Codex, OpenCode, Pi and other clients, Gemini's cached content, a prompt cache key, a Responses conversation or a connection's execution session, each with the parent it came from. A call that names none gets an identity derived from its leading instructions and first user message, kept apart for each client key by the key's hashed caller scope, and failing that a hash of its first messages.
- **Binding.** A session is bound, for its provider (or `mixed`, the scope of a call that may go to several) and its model, to the credential its first call picked. Later calls take that credential while it is ready, whatever its priority. When it isn't, the routing strategy picks again among the highest priority ready credentials and the session is bound to the new one; priority decides a first binding and a call without a session the same way. A failure the credential is to blame for unbinds it, a success keeps it for another `routing.session-affinity-ttl` (an hour when unset or not a positive Go duration, a second at least), and a removed credential's bindings go. A session with a parent or a conversation takes the credential that one is bound to; a subagent only while `routing.session-affinity-subagents` is on, the default. A change of the routing settings forgets every binding, as upstream's new selector does.
- **Codex Alpha Search** picks with affinity too, the payload's `id` naming the session. Nothing records a search's outcome, as upstream records none, so a failed search doesn't move its session.
- **Sessions are local routing keys only.** No session ID or derived identity is sent upstream, written into a request, logged or saved, and the usage statistics never record one (see [Usage statistics](#usage-statistics)). A credential's custom header that names `$CPA-SESSION-ID` is skipped for the same reason.

Deviations, each also noted in its module:

- **Bindings are held as hashes.** Each key, of a scope, a session and a model, is held as its SHA-256 hash, with whether it is a prompt cache key, which compaction needs; never as the session ID.
- **No goroutine.** The bindings live in the manager's state, behind its lock. Expired ones are swept by the first call at least half a TTL after the last sweep, where upstream runs a goroutine on a ticker, so there is no `Stop`. A group of bound keys is known by a sequence number, where upstream compares its credential, expiry and keys.
- **Nothing is logged or written into the call's metadata.** Upstream logs each binding with the start of its session ID, and writes the canonical session, its parent, the fork flag, the provider, the model and the derived session into the metadata for later stages, which aren't ported. A call carries only the hashed caller scope.
- **The body is read as `session::Payload` reads it.** A key given twice reads as its last value, where upstream's reads take the first; bytes that aren't UTF-8 read as U+FFFD; a body that doesn't parse, or nests more than 128 deep, names no session; and an object or array where a session ID was expected reads as its compact JSON, where gjson gives it as it was written (so one written over several lines, which upstream refuses for its line feeds, is taken).
- **Not ported:** the LCP matcher and its fingerprints, so a call that names no session goes straight to the derived identity and the message hash; `NormalizeToCanonicalUUID`; the session tree store; `LookupAffinity` and `Invalidate`, which only the plugin host calls; Home's shared bindings; and Antigravity's session header (`X-Http-Session-Id`) and request format.

Tests: `session_cache_test.go`, `info_test.go`, `identity_test.go`, `session_affinity_priority_test.go`, `session_affinity_metadata_test.go`, `selector_subagent_affinity_test.go`, `conductor_session_affinity_alias_test.go`, the affinity cases of `selector_test.go` and `selector_lcp_test.go`, and those of the service, handler, Alpha Search, model-not-found and DeepSeek tests are ported. Where upstream puts a derived session ID in a call's metadata, the ports send an `X-Session-Id` header; the Alpha Search test makes a fourth search, so that it fails without affinity. The `session-info` and `session-derive` parity suites (see [Checking parity](#checking-parity)) run upstream's `ExtractSessionInfo` and `DeriveID` and ours on the cases of upstream's tests and on seeded random headers and bodies.

### Grok shell clients

Grok's shell and pager are served in their own formats. Which one a client gets is decided by reading its own `User-Agent`, and nothing about the client is sent upstream: no header, ID or request field is made from the agent.

- `GET /v1/models` from a `grok-shell` agent gets the Grok shell's model list, in place of the OpenAI, Anthropic or Codex one, even with a `client_version` (`handlers::models::grok` in `open-ferry-server`).
- A Codex HTTP stream for a `grok-pager` or `grok-shell` agent gets Codex's keepalive events as `: keepalive` comments (`codex::stream` in `open-ferry-providers`). Upstream makes them only in its Codex HTTP stream, so no other executor's stream, and not the Codex Responses WebSocket's, has them, and the server's stream writer doesn't make them either.

Where it differs from upstream:

- **No Home model list.** Upstream builds the list from Home's models in Home mode, which isn't ported.
- **No plugin response interceptors.** Upstream hands the list to them before writing it (`WriteModelListResponse`); the plugin host isn't ported.
- **The Codex stream's agent comes from the call's headers.** Upstream also looks in the request's Gin context (`IsGrokClientContext`); the Codex executor is given the same headers as the call's options.

### xAI

The xAI executor (`open-ferry-providers`' `xai` module) serves `xai-api-key` credentials over HTTP and xAI's Responses WebSocket. It reuses the Codex executor's client, URL checks, secret redaction and `apply_patch` bridge, so like it:

- Requests say `User-Agent: open-ferry/<version>`, follow redirects only within their origin, and fail before anything is sent when the URL holds an ASCII control character.
- An answer that quotes a secret the request sent has it replaced with `[redacted]`, if the secret is of eight bytes or more, as every client error is (see `Policy::Client`): an error body, a stream's `response.failed` or `error` event, a compact answer's `error` object, and what a model says in a successful answer, which upstream passes on as it came. A stream, a call's that isn't streamed included, is redacted a line at a time and a compact answer whole, before either is read, so a `compaction_trigger`'s events are made from the redacted answer; a plain HTTP request's body is redacted whatever its status. The call's taps read the answer as it came.
- A `header:` attribute can't set a client identity header, Grok's CLI `X-XAI-Token-Auth` and `x-grok-client-*` among them (see `custom_headers`), nor the chat proxy's `x-authenticateresponse`.

Where it differs from upstream:

- **No made-up conversation.** `x-grok-conv-id` and `prompt_cache_key` are the `prompt_cache_key` the client sent, trimmed, or absent. Upstream also derives one from a Responses WebSocket's session, the request's metadata or the Claude Code prompt cache, or makes up a UUID for `grok-composer-` models.
- **No Grok CLI identity.** `X-XAI-Token-Auth`, `x-grok-client-*` and `x-authenticateresponse` are never sent, nor the `xai-grok-workspace` user agent, whatever a credential's `header:` attributes say.
- **One executor for HTTP and the Responses WebSocket.** Upstream wraps its HTTP and WebSocket executors in an `XAIAutoExecutor`; here `XaiExecutor` sends a streaming call over xAI's Responses WebSocket (`xai::websocket`) when the client is on the Responses WebSocket and the credential's `websockets` attribute (or metadata) is on, as upstream's does, and any other call over HTTP. The credential manager treats `xai` as `codex` for the Responses WebSocket's incremental input and pass-through, as upstream does. Only a Responses WebSocket client takes this route, so xAI's events reach it as they are; upstream's SSE translation for other clients isn't ported, nor are `RequiredUpstreamWebsocket`, the execution lifecycle binding, `UpstreamDisconnectChan` and `CloseXAIWebsocketSessionsForAuthID`, which the server uses none of (as for Codex).
- **xAI Responses WebSocket connections are Codex's.** They are kept in the executor's own sessions, where upstream's store is global, and behave as the Codex connections do (see [Deviations so far](#deviations-so-far)): reused only for the same credential, URL, proxy and token, closed with their session or on idling, closed when a call is dropped before it ends, and with the same limits on a message and the handshake. The handshake sends `Content-Type: application/json`, the credential's key, its configured headers (under the HTTP call's rules) and `x-grok-conv-id` only as the `prompt_cache_key` the client sent, with `User-Agent: open-ferry/<version>` where upstream's is Go's. A credential whose `base_url` is Grok's CLI chat proxy is dialled at xAI's API, as a compact call is sent there; upstream dials the proxy, which by its own comment answers an upgrade with a 405.
- **xAI's WebSocket messages have the credential's secret redacted.** Every message xAI sends on the WebSocket, a success or a failure, reaches the client with the secrets its handshake sent replaced with `[redacted]`, if the secret is of eight bytes or more, as every client error is (see `Policy::Client`); so do a refused handshake's body, an error event's message and the events made up for a `compaction_trigger`. Upstream passes them on as they came. The redaction comes before anything reads a message, so the session's transcript keeps the redacted text, but for the compaction a `compaction_trigger` gets, which it keeps as xAI sent it since it goes back to xAI; the call's taps (usage statistics and the request log) see each message as it came. A call that keeps a connection redacts the secrets that connection's handshake sent as well as its own, from xAI's messages and from its errors, as a credential's custom header may have changed since the connection opened.
- **An xAI WebSocket event whose response IDs are rewritten** for the client (a repeated ID becomes `<id>-xai-<n>`, as upstream's) is written by `serde_json`, keeping its key order, where Go writes it with sorted keys and HTML escaping. A bare error event's status beyond an HTTP status's range is 500, and a broken connection's errors are Codex's, naming xAI's executor.
- **Reasoning replay is kept in memory, and only for a session the client named.** Replay (`xai::replay`, `codex::xai_replay_cache`) is upstream's: for Claude and OpenAI Responses clients, the reasoning, assistant message and tool-call items of each completed Grok turn are kept under the model and session, and put back into the session's next request, except what the request already holds (see the module's docs). The session is found as the Codex replay finds it, so it is only one the client named (Claude Code's session and agent, the WebSocket execution session, a `prompt_cache_key`, Codex window or turn metadata, or Codex's session headers). Upstream's fallback to a session made from the client's proxy API key is never reached for xAI (it serves OpenAI Chat Completions clients alone, which xAI replay doesn't), and isn't ported. Like upstream's, a name the client chose is namespaced by a hash of the proxy key it called with (its first eight bytes in hex, kept in memory and never sent), so two callers can't share a turn by naming the same session; a request with no proxy key is replayed only in a WebSocket's `execution:` session. The server records a caller's key only when the config has proxy keys, so without any, a `prompt_cache_key` or Claude session alone isn't replayed. A turn stays an hour after it was last used, at most 10,240 are kept, and each write replaces the session's last turn. Home mode's shared KV store isn't ported, so it can't fail a request, and expired turns are dropped by the next write at most every ten minutes, not by a background task.
- **A tool schema's references are inlined within a budget.** Upstream inlines each local `$ref` in a function's parameters with a copy of its own, so a definition used twice by one used twice by another doubles with each level: seventeen levels turn 1.5 KB into 11.6 MB. Here inlining stops once the copies would outgrow the schema by more than 262,144 units, a unit being a value or a byte of a key or string (`xai::schema`'s `COPY_ALLOWANCE`), and the function gets the permissive object schema it gets for parameters xAI rejects, and isn't strict. Inlining also stops, with the same outcome, once its walk would go more than 64 levels deep, each object, array and reference followed counting one (`MAX_DEPTH`): the walk recurses and a chain of references costs nothing to copy, so a chain of 100,000 links (about 3 MB) would overflow the thread's stack and abort the process, where Go's growing stacks let upstream inline it. Sixty-four levels is far beyond a real schema, and keeps the inlined schema, which nests no deeper (a cycle's hint included), and the request that carries it a few levels down well within the 128 levels a JSON parser reads by default. A folded namespace lists that schema for such a child.
- **Image calls (`xai::executor::images`) are upstream's `executeImages`, with limits.** A streaming image call, or one with the `responses/compact` `alt`, gets a 400 before anything is sent; upstream sends the first to the Responses API and compacts the second, and no image handler asks for either. The body is shaped as a video call's is (its image references in xAI's shape, then the payload rules under protocol `openai` for the body's model) and sent as it came unless they change it; error bodies are read up to 4 MiB and a success's up to 50 MiB, both redacted of the request's secrets. The call's usage record names the body's model, the model xAI's answer names and no counts, as upstream's does.
- **Video calls (`xai::executor::videos`) are upstream's `executeVideos`, with limits.** A streaming video call, or one with the `responses/compact` `alt`, gets a 400 before anything is sent; upstream sends the first to the Responses API and compacts the second, and no video handler asks for either. As upstream's, the payload rules apply to the JSON body as to any call's, under protocol `openai` with no root (`payload::apply`, upstream's `NewPayloadFinalizer`), not as to a media body. The body is sent as it came unless its image references or a payload rule change it, and a changed body is written compactly in its own key order, where upstream's rewrite writes Go's sorted keys; a body that isn't a JSON object is sent without the rules. Error bodies are read up to 4 MiB and a success's up to 50 MiB, where upstream reads both whole, and both are redacted of the request's secrets as every xAI answer is. As upstream's, each call's usage record names the body's model (else the request's), the model xAI's answer names and no counts: a create, a retrieve and the lookup before a download make one each, and the download none.
- **Speech calls (`xai::executor::speech`) are upstream's `executeSpeech`, with limits.** The handler's body goes to `<base URL>/tts` (xAI's API in place of Grok's CLI chat proxy) with the payload rules under protocol `openai` for the body's model, and the audio comes back as it came with xAI's headers. A 404 is the request's alone, so the credential is neither cooled nor swapped, unless its body says the model is unknown or unavailable, as upstream's. A speech call with the `responses/compact` `alt`, which upstream compacts, or a streaming one, which upstream refuses with its own 400, gets the image and video calls' 400 before anything is sent; the speech endpoints make neither. The audio is read up to 256 MiB and an error body up to 4 MiB, where upstream reads both whole; the error body is redacted of the request's secrets, the audio isn't. An error body serde can't read is searched as text. The usage record names the body's model, no response model and no counts, as upstream's.
- **A finished video is downloaded by the executor** (`ProviderExecutor::download`), where upstream's handler builds an HTTP client of its own from the credential's proxy. It sends no key or header of the credential, as upstream's doesn't, but goes through the executor's shared clients, so it follows a redirect only within the URL's origin and says `User-Agent: open-ferry/<version>`; a URL with an ASCII control character fails before anything is sent. A success streams to the client as it comes; a failure's body is read up to 4 MiB and redacted of the URL's secret query parameters, the proxy's password and the credential's keys. The download isn't tapped, as upstream's isn't, and its status text is the status's canonical reason.
- **Token counts are estimated locally** with `o200k_base` as upstream does, but a JSON value is counted as `serde_json` writes it, compactly.
- **Only an API key is read.** A credential file from upstream's xAI sign-in gets the xAI models, but its access token isn't sent, so xAI refuses its calls (401).
- Usage records name `XAIExecutor` and read a turn's Codex usage and a compaction's OpenAI usage, as upstream's executor does, and `XAIWebsocketsExecutor` for a WebSocket call, read from its `response.completed` or `response.done` as upstream's WebSocket executor reads it (see [Usage statistics](#usage-statistics)).

Deliberately not ported:

- **xAI sign-in, token refresh (`xai_executor_auth.go`) and the Grok CLI chat proxy** (`cli-chat-proxy`), with its identity headers and user agent.
- **Session derivation** for `x-grok-conv-id` and `prompt_cache_key` (decision 3: only the client's own values).

### The config writer

`open_ferry_core::config::save` writes the config file back as upstream does: `save_preserving_comments` is `SaveConfigPreserveComments` (`internal/config/config_yaml.go`, with the saving half of `config_v8.go` and `config_v8_api.go`'s `ProjectV8ConfigAliases`), `update_nested_scalar` is `SaveConfigPreserveCommentsUpdateNestedScalar`, `write_file` is the management API's `WriteConfig` (`config_basic.go`), and `config::v8_edit::edit_v8` makes the v8 management writes (`ConfigV8`'s `PUT`, `PATCH` and `DELETE` in `config_v8.go`, with `config_auth_index.go`'s removal of the `auth-index` a read adds to the API keys). It reads and writes YAML with a port of yaml.v3 (`config::yaml3`, see [Other ported code](#other-ported-code)), so the bytes it writes are upstream's: comments, key order, quoting, indentation and anchors are kept where upstream keeps them, and flow collections are rewritten in block style where upstream rewrites them. The management routes that write the config call it through the writer the service gives them (see [Config writes](#config-writes)). Upstream calls `SaveConfigPreserveCommentsUpdateNestedScalar` when loading hashes a plain management key; loading never writes here, so only the parity suite calls `update_nested_scalar`. `write_as_is` is open-ferry's own: it writes a whole file as it is given, with the checks below, for `open-ferry init`. `tools/parity` runs it against upstream's on hand-written and random files (see [Checking parity](#checking-parity)).

Where it differs from upstream:

- **Every write is checked first.** The new file must load as a config, by the loader's rules and in its wording (`LoadConfig`'s), or nothing is written and the error says why. Upstream writes what it made without loading it, so a nested string set under a key that holds a number (`port` then `inner`) gives a file its own `LoadConfig` refuses (`failed to parse config file: yaml: unmarshal errors:` then `line 3: cannot unmarshal !!map into int`); open-ferry refuses the write with that message. Likewise, emptying an OAuth map (`oauth-excluded-models` and the like) whose key carries a line comment makes upstream write `oauth-excluded-models: # excluded` with `{}` on the next line at column 0, which its `LoadConfig` refuses (`yaml: line 4: could not find expected ':'`); open-ferry refuses the write in its loader's wording. The random cases find more, such as a list item holding a block scalar under a head comment. The parity suite reads each file upstream writes with upstream's own `LoadConfig`, and counts a write that refuses and open-ferry's loader refuses too as equivalent ("unloadable file refused, not written"). It has found no file upstream's `LoadConfig` reads and open-ferry's refuses.
- **Writes are atomic and keep one backup.** A temporary file in the same directory is written, flushed and renamed over the file, and the previous contents are kept as `<file name>.bak`, replaced on each write. The SHA-256 of what was written is recorded in `<file name>.sha256`, so an undo can tell a file changed since (as by a hand edit); the record is best effort, and a write that can't record removes the old record. `write_file_expecting` writes only while the file holds the bytes the change was worked out from. Upstream keeps neither. On Unix both keep the file's permissions, and a new file is created 0600, where upstream's `WriteConfig` creates it 0644. Upstream truncates the file and writes it in place. When the rename is refused with EBUSY or EXDEV, as Linux refuses it over a file that's a mount point of its own (a config bind-mounted alone into a container), the file is written in place too, as upstream does, after the backup is written.
- **A symbolic link at the path is refused**, as is another reparse point on Windows; upstream writes through it.
- **A file that isn't UTF-8 is refused** (`yaml: input is not valid UTF-8`); yaml.v3 also reads UTF-16.
- **The settings open-ferry doesn't type keep the file's values**: `plugins` (`plugins.configs` included), `pprof`, `claude-code`, the credential tuning sections, `discovery`, the Antigravity and Devin sections, the Codex live relay, the client impersonation settings (the header defaults, Claude's `cloak`, `fingerprint-profile`) and unknown keys. Upstream writes them from what it decoded, which holds the same values but can respell them (`yes` as `true`); writes `plugins.dir` as `ResolvePluginsDir` made it (cleaned with the system's separators, `~` expanded, `plugins` when empty); and replaces `plugins.configs` from the running config (`replacePluginConfigsSubtree`), with the plugin IDs sorted and plain, dropping it when empty. A management write's config comes from the file, so the two agree but for those changes (the parity suite's known differences `plugins-dir-cleaned` and `plugins-configs-rebuilt`). Upstream's `plugins.configs` subtree, re-encoded from each plugin's decoded node (`PluginInstanceConfig.MarshalYAML`), carries the plugin's comments, some on other nodes than in the file: a comment ending a plugin's settings that end the file goes on the last list item, not on the list's key. `preserveV8Comments`, at the end of `restoreV8Layout` on every save, then puts the file's comments back on their keys, so upstream writes such a comment twice in a row; open-ferry writes it once (counted as equivalent by the parity suite). Only `plugins.configs` is taken whole from the decoded config, and the other settings are generated without comments, so this can't happen elsewhere. A key upstream adds to these sections with its default is added here too.
- **The config passed in isn't changed.** After a save that moves the file to the v8 layout, upstream sets the config's `OAuthOnlyFields` (which settings the file gives under `oauth.providers`) from the file it wrote. The file written is the same; the caller reloads it, as upstream's watcher reloads it too.
- **A migrated file is checked by the load check.** Upstream decodes a file it migrated once more and fails with `decode migrated config: ...`; here the load check refuses it, in the loader's wording.
- **A payload value that is a mapping with a key that isn't a string, or a timestamp whose zone is 24 hours or more from UTC, can't be written**, and the save fails naming the rule; the loader keeps neither. Upstream writes them.
- **Aliases expand within limits.** An alias inside the node its anchor names is `yaml: anchor 'a' value contains itself`, where upstream's expansion recurses until the stack overflows; more than 2^20 nodes is `yaml: document contains excessive aliasing`, and nesting deeper than 256 levels `yaml: exceeded max depth of 256` (yaml.v3 allows 10000). Where upstream would index past the end of a node, nothing happens.
- **I/O errors** are worded `open <path>: <error>` with the platform's text, which differs from Go's.
- **Loading still never writes.** Upstream's `LoadConfig` writes a plain `secret-key`'s bcrypt hash back to the file and removes legacy fields that a v8 field overrides; open-ferry's loader writes nothing (see the management API's foundation).

### Sign-in pages

A browser sign-in ends on a page of open-ferry's own (`oauth::page` in `open-ferry-providers`). The CLI login's callback server (`oauth`) answers with it, and so do the main server's callback pages, `/anthropic/callback` and `/codex/callback` (`oauth::callback` in `open-ferry-management`), where a sign-in started from the dashboard ends. The page says how the sign-in ended (signed in, failed and why, or still finishing) and where to go next: back to the terminal or to the dashboard.

- **The page has its own design and words.** It is one self-contained document in the dashboard's colours (its `--of-*` tokens, light or dark as the system prefers), with the dashboard's mark inlined. It loads nothing, runs no script, and HTML-escapes all text it didn't write itself. Upstream's CLI page (`LoginSuccessHtml`) and the main server's (`oauthCallbackSuccessHTML`) promise that the window closes by itself, in 10 and 5 seconds, with a script calling `window.close()`, which browsers allow only for a window a script opened; this page says the tab can be closed. Upstream's CLI page also links to the provider's site, taking a `platform_url` from the query into its HTML unescaped; this page takes nothing from the query.
- **The page sends security headers.** It sends `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, since the callback's URL holds the code. It also sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and a content security policy of `default-src 'none'` that allows only the page's own style, by its SHA-256 hash, and `data:` images. The CLI callback's redirect sends the first two. Upstream sends none of them.
- **A failure page answers 400; a signed-in or still-finishing page answers 200.** Upstream's CLI callback answers a failed callback 400, in plain text; the main server's pages answer 200 whatever happened.
- **The CLI's success page waits for the login's outcome.** The callback sends the browser on to `/success`, as upstream's does. The page there waits up to 8 seconds for the login to exchange the code and save the credential. Then it says how that went, with the reason redacted of the code and the PKCE verifier, or that the sign-in is still finishing and the terminal shows the result. 8 seconds keeps the answer inside the connection's 10-second deadline. Upstream's page says the login succeeded at once, before the code is exchanged. `/success` asked for before a code has come answers 400, saying there is nothing to report.
- **The CLI's callback server lasts until the credential is saved.** Upstream's login stops it when it returns: after the code exchange, before the credential is saved. Here it stops once the save is done and the success page has answered. A browser that hasn't asked for the page by then gets 5 more seconds. A login that fails after the callback stops it the same way, once the page has said why.
- **The main server's callback pages wait for the login's outcome.** A page that hands its login a code waits up to 30 seconds for the login to exchange it and save the credential. Then it says how that went, or that the sign-in is still finishing and the dashboard shows the result. An exchange takes a second or two as a rule, but may take up to its 60-second limit; 30 seconds is half the minute a reverse proxy commonly waits for an answer. Cancelling the login, or shutting the service down, ends the wait at once: the page says the sign-in stopped. Only the page whose code the login took says why the login failed (the session's status, with the code and the PKCE verifier redacted). The page loaded again, or another callback's page, says how the login ended, but not why it failed. Upstream answers at once, whatever the callback held, with a page saying the login succeeded.
- **The main server's callback pages say when they hand over nothing.** A page without a `state` says it isn't from a sign-in. A page whose state no pending login of its provider has says no sign-in is waiting for it, unless that login has ended: then it says how. Upstream answers each with its success page.

### The management API

`open-ferry-management` serves upstream's management routes in parts, each route under both of its names: its v0 path under `/v0/management` and its v8 path under `/v8/management`. Each module documents the routes it serves. Bodies, statuses and headers are written as gin and Go's `encoding/json` write them, and request bodies, query strings, URLs and client addresses are read as gin and Go read them. The tests check them against answers recorded from Go programs built with upstream's `go.mod` (gin v1.10.1, Go 1.26 language settings).

The routes that change the config save it through the config writer the service gives the API (see [The config writer](#the-config-writer)), then have the service load it again (see [Config writes](#config-writes)). The binary's service always gives one, over the config file it was started with. Nothing is written when the config is loaded.

#### The foundation

What every part shares, and the deviations that apply to all of them:

- **Routes are registered by module.** Each module gives its routes with their access: `Key` (the management key must be set and offered, as upstream's management routes), `Availability` (the key must be set, as upstream's OAuth callback) or `Open` (nothing, as the main server's OAuth callback pages). Routes on one path are served together, each with its own access.

- **Unported paths answer an empty 404.** Every other path under `/v0/management` or `/v8/management`, and every other method on a management path, `HEAD` included, answers an empty 404, as upstream answers a path it has no route for, whatever the method. Another method on an `Open` route outside those paths answers the server's `404 page not found`, as gin does.

- **Credentials reach the service through its loop.** A credential the management API saves, changes or removes is applied by the service's event loop, which the handler waits for, where upstream's `runtimeAuthSyncHook` calls the credential manager directly. Once the loop has stopped, as on shutdown, the change fails with a 503 (`credential sync unavailable: the service has stopped`); a handler that writes credentials while the API has no credential store answers 503 `{"error":"credential store unavailable"}`. Changes are ordered as upstream's service orders them: a change at or below the last revision applied to its credential is skipped, and a credential the API changed is refused, keeping the newer one, once the manager has changed it since, as by a token refresh; the handler is told either was applied, as upstream's is. Revisions come from one counter for every credential, and the watcher takes an event's before it reads the file or finds it gone, where upstream stamps an update once it is built from what was read, so a report read just before the API saved a change, and applied after it, could undo the change. A report for a file that is gone by the time it is applied unregisters its credential rather than bringing it back.

- **Saved logins and imports keep the settings of the file they replace** (upstream's `saveTokenRecord` and `mergeExistingAuthFileMetadata`), and a Claude login replaces the file of the same account saved under an older name, as the `login` command does. The file is read from and saved in the service's auth directory, where upstream points its token store at the config's `auth-dir` on each save. When there is no file, a registered credential lends its settings only if its metadata isn't empty, matched by ID and then by a file name that isn't empty, the first by ID; upstream also takes empty metadata, matches an empty file name, and takes whichever its map yields first. The service makes the credential from the saved file and logs a file it can't read one from, where upstream makes it first and fails with `synthesize persisted auth failed`. The merge, the save, the readback and the call telling the service hold the credential lock that status and field changes, uploads and deletes hold, so the change takes its revision under it, and the call is awaited once the lock is released; upstream takes none, so a status change made meanwhile could save its stale copy over the new credential. Neither the file replaced nor the one saved is read through a symlink or, on Windows, any reparse point, and a symlink where the file would be saved is refused (checked just before the save): the save fails with `<path> is a symlink`, where upstream reads and writes through it. Upstream's post-auth hook, which only plugins and embedders set, isn't ported.

- **Auth files are written atomically.** Writing a file in the auth directory writes a temporary file there and renames it over the target, where upstream's `os.WriteFile` truncates the file and writes it in place. A symlink is written through to its target, as `os.WriteFile` does, but a dangling one is replaced by the file, where `os.WriteFile` creates the file it points to. Removing a file removes a symlink itself.

- **Paths match exactly.** While a key is set, gin redirects a ported path with a trailing slash (301 for `GET`, else 307) and matches a percent-encoded path decoded. Both get the empty 404 here, as they do on the server's other routes.

- **Loading never writes the config.** Upstream hashes a plain `secret-key` with bcrypt when it loads the config and writes the hash back. We keep the key as the file has it and compare a plain key as written, in constant time and in full; upstream's bcrypt reads only the first 72 bytes, and a longer plain key fails to load.

- **The failed-attempt record is bounded.** It holds at most 4096 addresses; when it's full, the address least recently active is forgotten, which ends any ban on it early. Idle entries are purged when the record is next written, at most hourly, rather than by an hourly timer. Upstream's record has no bound.

- **`X-CPA-VERSION` is this crate's version.** `X-CPA-COMMIT` and `X-CPA-BUILD-DATE` come from `OPEN_FERRY_COMMIT` and `OPEN_FERRY_BUILD_DATE` at build time, else `none` and `unknown`. `X-CPA-SUPPORT-PLUGIN` isn't sent.

- **JSON corner cases.** A request body string holding an unpaired surrogate escape such as `\ud800` fails to decode; Go reads U+FFFD. A value from a credential's metadata is held by `serde_json`, so an integer `-0` is written back as `0`, and a number beyond `f64`'s range, which Go fails to decode, is written as it was read. `ToUpper` on a method leaves a Greek letter with a subscript iota unchanged; the method is refused either way.

#### Listing, API calls and quota

| Route | v8 route |
|---|---|
| `GET /v0/management/auth-files` | `GET /v8/management/credentials` |
| `GET /v0/management/auth-files/models` | `GET /v8/management/credentials/models` |
| `POST /v0/management/api-call` | `POST /v8/management/requests/api-call` |
| `POST /v0/management/reset-quota` | `POST /v8/management/routing/cooldown/reset` |

Deviations, each also noted in its module:

- **`auth-files` shows quota observations only for Claude and Codex.** Upstream's include Devin's, which isn't ported. `supports_quota` and `quota_provider` come only from a `quota_probe` in a credential's metadata, since there is no plugin host.

- **`auth-files` times are in UTC.** Upstream writes some, such as file times and times read from files, in the server's time zone. One clock reading serves a whole listing, where upstream reads the clock for each credential. Unpaged, credentials whose names differ only in case keep the manager's order (by ID); upstream's sort isn't stable.

- **`api-call` never refreshes a credential.** An Antigravity, Meta or xAI credential's token is looked up as any other's. Upstream refreshes an Antigravity or xAI token about to expire, mints a Meta key from its `dca_token`, and answers `auth token refresh failed` when that fails; it also never takes an xAI credential's `id_token`.

- **`api-call` sends `User-Agent: open-ferry/<version>`** when the caller sends none, where upstream sends Go's `Go-http-client/1.1` (or `/2.0`). An empty `User-Agent` from the caller sends none, as upstream. Without an `Accept` from the caller, the HTTP client sends `Accept: */*`; upstream sends none. Otherwise the request carries exactly the caller's headers and what HTTP needs.

- **`api-call` reads at most 16 MiB of a response**, compressed or not; a larger one gives a 502 `failed to read response`. Upstream reads any size. Request bodies over 16 MiB get a 413 before they are read; upstream reads any size.

- **`api-call` uses Rust's HTTP stack.** The header map is applied in the order of its names (upstream's order is random, which matters only for names that differ in case alone). A request with a `Host` header goes over HTTP/1.1 so the header is sent as given; upstream may send it over HTTP/2 as `:authority`. A `Host` outside ASCII gives a 502, where upstream converts it to Punycode. The URL sent, a redirect's target and its `Referer` are the `url` crate's reading of the URL, which may normalize differently from Go's; a URL that the `url` crate refuses, such as one with an IPv6 zone, gives a 502. Through a forwarding proxy the request line names the `Host` header's host, as upstream's does, but as the `url` crate reads it (lowercased, without a default port), and one it refuses gives a 502. A `CONNECT` names a host and port alone, where upstream names the URL's path when it has one, and the whole URL through a forwarding proxy. A 2xx answer to `CONNECT` with a chunked body, and an HTTP/1.0 response with a `Transfer-Encoding`, give a 502; upstream reads them. `Expect: 100-continue` is sent but not waited on. SOCKS5 proxies are accepted but a call through one fails with a 502. A client is kept per proxy, at most 16, where upstream builds a connection pool per call.

- **Only Gemini, Claude, Codex and OpenAI-compatible API keys have proxies in the config**, so a credential from another provider's key never finds its proxy there. As upstream, a Vertex AI key's proxy isn't looked up there either; its credential carries it.

- **`reset-quota` picks the first credential by ID** when two share an index; upstream takes whichever its map yields first.

- **`auth-files` entries have open-ferry's `quota_checks`** while `routing.quota.check-after` holds one of the credential's quota rests: each rest's `scope`, `model_key`, `state`, `next_check_at`, `provider_reset_at` and `wait_seconds` (see [Added in open-ferry: routing by quota](#added-in-open-ferry-routing-by-quota)). An entry without one has no such field, so upstream's shape is kept. `reset-quota` ends those rests too.

#### Credential files

| Route | v8 route |
|---|---|
| `GET /v0/management/auth-files/download` | `GET /v8/management/credentials/download` |
| `POST /v0/management/auth-files` | `POST /v8/management/credentials` |
| `DELETE /v0/management/auth-files` | `DELETE /v8/management/credentials` |
| `POST /v0/management/vertex/import` | `POST /v8/management/oauth/import?provider=vertex` |

Deviations, each also noted in its module:

- **Names are checked as Windows needs them, on every system.** A name holding `/`, `\` or `:` (so no path, drive, UNC share or NTFS stream), a control character or one of `<>"|?*`, ending in `.` or a space, or naming a Windows device such as `CON` or `nul.json`, answers 400 `invalid name`. Upstream refuses only a blank name, a separator and, on Windows, a volume name, and checks an uploaded file's name for `.json` only. An uploaded file's name is read from its part's `Content-Disposition` as Go reads it (RFC 2231 continuations and extended `filename*` values included), then is what follows the last `/` or `\` on every system, a drive such as `C:` kept (so refused); Go splits only at `/` outside Windows, and drops the drive on Windows. A field or file name's bytes that aren't UTF-8 are read as U+FFFD each, so such a file is saved with U+FFFD in its name. Go keeps the bytes outside Windows, and on Windows reads them as U+FFFD too, but for an encoded surrogate. On Windows a delete matches a credential's ID or file name regardless of case when nothing matches exactly, as the file system does. A Vertex `project_id` that gives a file name Windows can't hold answers 400 `invalid service account`.

- **An upload must hold a credential the service serves.** It is written only if the core's file synthesizer reads a credential from it (a JSON object with a type the service serves), so a file that doesn't parse never replaces the one there. Upstream also writes `null`, a file without a type (registering it as provider `unknown`) and a Gemini CLI file. The reason after `invalid auth file: `, and the `message` of the Vertex import's `invalid json`, may read differently from Go's. The Vertex import reads the key file with a JSON parser that takes at most 127 levels of nesting, the account's own object the first: a file nested 128 or more deep, as one with a field holding 127 nested arrays, answers 400 `invalid json` (`recursion limit exceeded at line ... column ...`), where Go reads up to 10000 levels. The saved file holds the account a level deeper, under `service_account`, and the service reads it with the same limit, so an account exactly 127 deep is saved and answers 200 but isn't served (the service logs the file); Go serves it.

- **Nothing is read or written through a symlink.** Uploads and imports are written atomically, as every auth file is. A symlink where the file would go is refused, checked just before the write: an upload with `failed to write file: ... is a symlink`, an import with 500 `save_failed`. A download refuses a symlink at the file's name, and on Windows any reparse point such as a junction, with 500 `failed to read file: <path> is a symlink`. That check is made on the file opened, so no link can be put there in between: Windows opens a link itself rather than its target, and on Unix the file opened must be the one found at the name. Upstream reads and writes through it, in place. The Vertex credential is written compact, as the store writes every credential, rather than indented; its service account's numbers are written as they came, where Go writes them as float64, and its key's PEM headers are dropped.

- **Sizes are bounded.** A form or body over 32 MiB answers 413 `request body too large`, a file over 8 MiB (the most the service reads) 413 `auth file too large`, and a form of more than 1000 parts 400 `invalid multipart form: multipart: message too large`, as Go's does; the reason after `invalid multipart form: ` is the form parser's. A download of a file over 8 MiB fails with a 500. Upstream takes any size.

- **Deletes stay at the top of the auth directory.** A delete removes only a `*.json` file there. When the credential named has its file elsewhere, the delete answers 409 `auth file is outside the auth directory` and nothing changes, and one whose file isn't `*.json` answers 400 `name must end with .json`; upstream removes the file wherever it is. The file is there when the directory its path names is the auth directory itself, as the file system resolves both, so case, `.`, `..` and links count as it counts them; a directory it can't resolve, as one that is gone, is elsewhere. `?all=true` deletes in name order, skips names that aren't valid UTF-8, and stops at the first file the service can't be told of. The plugin host isn't ported, so there are no plugin credentials to refuse deleting.

- **A change the service can't be told of answers 503.** When the service has stopped, an upload, delete or import answers 503 with the reason, and the file stays written or removed; upstream registers the credential itself. Without a credential store the Vertex import answers 503 `credential store unavailable` before reading the form, where upstream answers 500 `save_failed`.

#### Credential state

| Route | v8 route |
|---|---|
| `PATCH /v0/management/auth-files/status` | `PATCH /v8/management/credentials/status` |
| `PATCH /v0/management/auth-files/fields` | `PATCH /v8/management/credentials/fields` |
| `POST /v0/management/auth-files/refresh` | `POST /v8/management/credentials/refresh` |

A status or field change is saved to the credential's file, then applied by the service, which registers the credential's models again, so a credential turned back on gets its models back. The credential lock is never held while the service applies a change. A refresh refreshes one credential at a time per ID, and refreshing all of them runs at most the manager's `refresh_workers` at once. As upstream, the refresh answer holds the refreshed credential's tokens; the route is behind the management key.

Deviations, each also noted in its module:

- **Turning a config API key on or off doesn't touch the token store.** As upstream, `auth-files/status` on a credential from a config API key adds `*` to the key's `excluded-models` (or removes it), saves the config as [Config writes](#config-writes) describes, and answers with `"via":"config:excluded-models"`; a change through the v8 name saves the file in the v8 layout. Upstream then asks its token store to delete the credential's ID, which names no file; that call is left out. As upstream, `auth-files/fields` on such a credential changes it in the running service only.

- **Status and field changes answer 503 when the service can't take them**, as the foundation's other writes do: `credential store unavailable` without a credential store, and the service's error once it has stopped. Upstream answers 500 when its hook fails.

- **Fields are applied in body order**, and the first bad one is reported. Upstream walks a Go map, so with two bad fields the one it reports varies, as does which of two headers that trim to the same name wins.

- **A field change holds the credential lock**, as a status change does; upstream takes none. A change to a credential removed meanwhile answers 404 `auth file not found`, where upstream hands its stale copy to the hook and registers it again.

- **Lookups take the first credential by ID** when two match a name; upstream takes whichever its map yields first. A refresh body that fails to decode answers 400 `invalid request body` without Go's decoder error after it. A refresh's query value that isn't UTF-8 has each bad byte read as U+FFFD.

- **A field change can't nest deeper than the store reads back.** A body nested more than 127 deep is refused as an invalid request body, and so is a field whose dotted parts plus its value's own depth pass 127, which would nest the credential's file deeper than `serde_json` reads it. Go's decoder allows 10000, and upstream builds whatever a dotted name asks for, writing a file it can't read back past that.

- **The refreshed credential is written field by field as Go writes upstream's `Auth`**, with `"unknown"` for a status that isn't known, where Go writes `""`.

- **There are no plugin virtual credentials**, since there is no plugin host, so none of upstream's handling of them is ported (409 for a virtual child, turning every credential of a source file on or off).

#### OAuth logins

Claude and Codex logins, with the providers' official OAuth flows only:

| Route | v8 route | Access |
|---|---|---|
| `GET /v0/management/anthropic-auth-url` | `GET /v8/management/oauth/auth-url?provider=claude` | `Key` |
| `GET /v0/management/codex-auth-url` | `GET /v8/management/oauth/auth-url?provider=codex` | `Key` |
| `GET /v0/management/get-auth-status` | `GET /v8/management/oauth/status` | `Key` |
| `DELETE /v0/management/oauth-session` | `DELETE /v8/management/oauth/session` | `Key` |
| `GET`, `POST /v0/management/oauth-callback` | `GET`, `POST /v8/management/oauth/callback` | `Availability` |
| `GET /anthropic/callback`, `GET /codex/callback` (the main server) | | `Open` |

A login answers its authorization URL and `state` at once, then waits up to 5 minutes for its callback. It exchanges the code at the provider's token endpoint, through the config's `proxy-url` and with `User-Agent: open-ferry/<version>`, within 60 seconds, and saves the credential as other saved logins are saved (above). With `is_webui`, a callback forwarder on the redirect URI's port (54545 for Claude, 1455 for Codex) sends the browser on to the main server's callback page, over `https` when TLS is on; while that port is held elsewhere, the login answers 500 `{"error":"failed to start callback server"}`. The callback routes only look up a `state` of 1 to 128 letters, digits, `-`, `_` and `.`, without `..`.

Deviations, each also noted in its module:

- **A callback reaches its login in memory.** Upstream writes it to `.oauth-<provider>-<state>.oauth` in the auth directory, which the login polls twice a second. Nothing is written here, and no directory made, so `oauth-callback` never answers 500 `failed to persist oauth callback`. A session takes its first callback; a later one, while it is still pending, is answered `ok` and dropped, where upstream's login reads whichever file was written last before it looks.

- **Sessions are bounded.** At most 1024 are kept; past that, a login answers 429 `{"error":"too many oauth sessions"}` until some expire. Upstream keeps any number.

- **A cancelled login stops at once**, wherever it is but while it saves, and stops its forwarder. A login cancelled after its callback came and before its exchange sends no token request, and one cancelled during its exchange drops the request. Upstream's login notices a cancel on its next poll, and one cancelled during its exchange runs the exchange to its end, then saves nothing.

- **The exchange has 60 seconds**, until the credential is made; past that, the session fails with `Timeout exchanging authorization code for tokens`. Upstream's has no deadline.

- **Shutting down stops the logins.** When the service shuts down, every login stops, as a cancelled one does, and drops its session; a login started after that answers 503 `{"error":"server shutting down"}`. Upstream's logins run until the process exits.

- **The token endpoint's answer is kept out of the logs and from strangers**, as it may quote the code and the PKCE verifier. A failed exchange is logged with a fixed message and the endpoint's status, where upstream logs the error with the answer in it. `oauth-callback`, which needs no key, answers a callback for a failed login 409 `{"error":"oauth flow failed","status":"error"}`, where upstream answers the session's status. That status keeps upstream's wording, a Codex one quoting the answer, but with the login's code and verifier replaced by `[redacted]`. `get-auth-status` answers it with the key, and the callback page whose code the login took shows it.

- **The callback pages say how the login ended**, once it has, waiting up to 30 seconds, and answer 400 for a failure. Upstream's say it succeeded, at once, whatever happened. See [Sign-in pages](#sign-in-pages).

- **A saved credential is logged without the account's email.** The line, at info, names the file without its directory and with its email masked (`claude-j***@e***.com.json`, see [Log files and config changes](#log-files-and-config-changes)); upstream prints the full path to standard output.

- **A login that can't start its forwarder, or can't tell the server's port, drops its session**, where upstream leaves it pending with nothing waiting on it.

- **Forwarders listen on 127.0.0.1 only**, where upstream listens on every interface. A connection is closed 5 seconds after it connected or was last answered; upstream gives 5 seconds each to send a request's headers and to take the answer, and leaves an idle connection open. A stopped forwarder closes its listener at once and leaves its open connections to their deadline, where upstream gives them up to 2 seconds.

- **The `state` is 32 random bytes in unpadded URL-safe base64**; upstream's is 16 in hex.

- **A credential without an email isn't saved.** The session fails with `Failed to save authentication tokens:` and the reason, where upstream saves it under a name without an email. A Codex account ID is trimmed before it is hashed for the file name. A Claude login saves no device IDs.

- **There is no `State code error` status**, as a callback can't carry another login's state, and a login's status never polls a plugin.

- **A code that isn't UTF-8**, once decoded from the query, is read with each bad byte as U+FFFD; Go keeps its bytes.

Deviations, each also noted in its module:

- **`GET config` writes only the sections open-ferry types.** Plugins, pprof, the Antigravity and Devin sections and the client impersonation settings are left out. An empty list is written as `null`, so `api-keys` gives `null` where the file has `[]`; upstream gives `[]`.

- **`config.yaml` sends the file as it is**, under both names; upstream's v8 route sends it migrated to the v8 layout. So it shows the management key as the file holds it.

- **The v8 reads show a plain management key as a bcrypt hash**, as upstream does once it has hashed the key into the file. Since the file keeps the plain key here, the hash is made when it is read (once per key while the process runs) and differs from one run to the next.

- **Config errors are worded as open-ferry's loader words them.** A file that doesn't load is `invalid_config`, but a syntax error is worded as the saphyr parser words it, and a type error doesn't quote the value. A read error's message is the operating system's. saphyr also reads a few files yaml.v3 refuses, such as one with a tab before a top-level key, and refuses a few it reads, such as one with a tab right after a key's `:`.

- **An alias used as a mapping key needs a space, a line break or the end of the file after its `:`** when the `:` follows its name directly (`*k: v`). Otherwise saphyr takes the `:` as part of the name, so `{*k:1}` and `[*k:]` are an `unknown anchor` error where yaml.v3 reads them.

- **Aliases may expand to at most 64 MiB of text.** A file whose settings take more than 64 MiB of text through aliases doesn't load (`yaml: document contains excessive aliasing`), and a v8 read of a value that does is a 500 `decode_failed`. yaml.v3 shares one Go string among an alias's copies, so upstream reads them; its limit on the ratio of aliases to nodes applies here too.

- **A v8 value Go's JSON encoder can't write is a 500 `{"error":"encode_failed"}`**: a mapping with a key that isn't a string, an infinite or NaN float, or a time in a zone a day or more from UTC. Upstream answers 200 with no body.

- **`model-definitions` knows only the channels open-ferry serves**: `claude`, `gemini`, `gemini-interactions` (the Gemini models, as upstream lists them), `vertex`, `codex`, `xai` (also `x-ai` and `grok`) and `meta` (also `muse`). Upstream's others (`aistudio`, `kimi` and its spellings `kimi-ai`, `kimi.ai` and `kimi.com`, `antigravity` and `devin`) answer 400 `unknown channel`. The `xai` list ends with upstream's three built-in image models and three video models, as upstream's does. A model's `config`, the client headers upstream sends for it, isn't written.

- **`latest-version` asks for open-ferry's releases as `open-ferry/<version>`**, where upstream asks for CLIProxyAPI's as `CLIProxyAPI`. Without a proxy in `proxy-url` it goes direct, where upstream follows `HTTP_PROXY` and `HTTPS_PROXY`. Redirects aren't followed. The token is the config's `server.github-token`, else one from `GITHUB_TOKEN` or `github_token`, not `GITSTORE_GIT_TOKEN`. Errors are worded as Rust's HTTP client words them, and a release that doesn't decode gives a fixed message (or `EOF` for an empty body) where upstream gives Go's decoder's error. A release is answered as soon as its JSON value is complete, as upstream answers it, but one that comes in so many pieces that checking after each would parse more than 16 MiB is checked after that only where its brackets close; so a body that isn't JSON may be read on until it ends, the 16 MiB limit or the deadline, where Go's decoder stops at the first byte that can't be JSON.

All take the management key. The service gives the API a config writer over the config file it was started with. Each change is made under one lock: the config is copied, the copy changed and saved by the config writer, and the saved copy becomes the config the handlers read. The service then has its file watcher load the file at once, as upstream's reload hook calls `ReloadConfigIfChanged`, so the change takes effect without waiting for the watcher's debounce, and the handler answers once the service has applied it. With no watcher running, the service loads the file itself; once it has stopped, as on shutdown, a save still goes to the file and is loaded at the next start. A v0 write saves the file in the layout it has; a v8 write saves it in the v8 layout. The v8 writes hand their method, path and body to the writer, which reads the file in the v8 layout, makes the change, checks it and saves it. A save the writer refuses answers 500 `{"error":"failed to save config: ..."}`, or `write_failed` for `PUT config.yaml` and the v8 writes, and changes nothing. A credential from a config API key is turned on and off through the config too (see [Credential state](#credential-state)).

Deviations, each also noted in its module:

- **No writer, no write.** Without a config writer, every route that changes the config answers 503 `{"error":"config writer unavailable"}` before it reads its body, and changes nothing. Upstream always has a path to save to, and so does the binary, whose service always gives the API a writer; only a management state built without one, as in a test, answers 503.

- **A failed save changes nothing.** Upstream changes its config before saving and keeps the change when the save fails, so later reads and saves show a change the file never got.

- **The answer waits for the reload.** Upstream answers first and reloads in the background, except for a status change on a config API key. It also numbers its reloads and skips one older than a reload already applied. Here the reload goes through the file watcher, with the hash it keeps of the file, and what the watcher reads is applied in the order it read it, so a config read before a save is never applied after it and there is nothing to skip. Once the service has loaded the file again, its `auth-dir` is the resolved directory, so a later save writes it resolved; upstream resolves it at start, so its first save does too.

- **`PUT config.yaml` has the service load the file at once**, where upstream leaves the change to the file watcher; the config the handlers read is the one the body loaded as, so there is no `reload_failed` answer. The body is checked by loading it in memory, where upstream writes a temporary file beside the config and answers 500 `write_failed` with the system's message when it can't. YAML errors are worded as open-ferry's loader words them, and a legacy `weight` that is a string or a boolean answers 422 `invalid_config`, where upstream answers 400 `invalid_yaml`. A plain management key in the body stays plain in the file, where upstream hashes it into the file when it next loads it. A file that can't be written answers `failed to write config` without the system's message.

- **A v8 path that isn't UTF-8** answers 400 `invalid_path` to `PUT` and `PATCH`, and 404 `not_found` to `DELETE`, before the file is read. Upstream uses its bytes as a key.

- **The v8 writes are checked as upstream checks them, and once more.** The edited file must decode, leave the fields Home owns as they were, load as a config and pass `ValidateV8Config`, as upstream's must; then the bytes are checked to load as they are written, and written atomically (see [The config writer](#the-config-writer)). A path of more than 256 keys answers 400 `invalid_path`, where upstream creates the mappings. The port of `ValidateV8Config` checks the keys as yaml.v3's strict decode does, but not the values' types: the load check covers those of the settings open-ferry types, and a value of the wrong type in a setting it doesn't type passes. The rest are in `config::v8_edit`.

- **The client impersonation settings are skipped** wherever a request gives them, whatever their value: a Claude key's `cloak` and `fingerprint-profile`, and a Codex key's `disable-codex-cloaking`. Upstream checks them. The file keeps the ones it has, as the writer keeps every setting it doesn't type: a Claude `PUT` of the list a read shows, with a key added, keeps each key's `cloak` and `fingerprint-profile` as the file has them, as the dashboard's adding a key needs. Upstream, sent a list without them, keeps only the cloak's `mode` of the key it replaces.

- **Maps iterate in key order** when a list is cleaned up: where two OAuth channels lower-case to the same name, or two header names trim to the same one, the one that sorts last wins. Upstream's winner depends on Go's map order.

- **Bodies are read as Go's decoder reads them into upstream's types, with three exceptions.** A key given more than once takes its last value, where Go merges a later object or list into the earlier one and a later `null` leaves a plain field as it was. Values nest at most 128 deep; Go allows 10000. A string holding an unpaired UTF-16 surrogate escape fails the read; Go reads U+FFFD.

Tests: upstream's route tests of the key lists (`config_weight_test.go`, `config_priority_test.go`, `config_disable_cooling_test.go`, `config_codex_alpha_search_test.go`, `config_lists_delete_keys_test.go`, `config_meta_key_test.go`, `config_xai_key_test.go` and `TestPatchClaudeKeyPriority`), `config_basic_weight_test.go` and `config_apikey_disable_test.go` are ported, checking the config the writer is asked to save. Their checks of the file written, and the tests of the v8 writes in `config_v8_test.go`, `config_v8_compatibility_test.go`, `config_v8_client_test.go`, `config_v8_upstream_test.go` and cases 5, 6 and 10 of `TestConfigV8APIKeysExposeAuthIndex_Issue6287`, are ported over a config file in a temporary directory. The rest of `config_claude_key_test.go` and `config_codex_disable_cloaking_test.go` are dropped: they test client impersonation settings.

## Observability

Upstream's request logs, log files, usage statistics, payload rules and saved cooldowns are ported, each in a subsection below. Only the usage queue's Redis protocol isn't (see [The usage queue over RESP](#the-usage-queue-over-resp)).

### The foundation

What the parts share is in place:

- **A context for each request.** The server's outermost layer gives every request a `RequestContext` (`open_ferry_core::observe`): a version 7 UUID as its ID, when it started, its method and route, the connection's address and the client's address resolved through `trusted-proxies`, `X-Forwarded-For`, the client's `User-Agent`, the client key once it is checked, and the credential the manager picks. The access line is logged from it.
- **Taps on the upstream traffic.** Each call carries an `Observation`: the context, and the taps the request log and the usage statistics give for it, none while both are off. The Claude, Codex (HTTP and WebSocket), Gemini, Vertex AI, Meta and OpenAI-compatible executors and the Codex Alpha Search pass-through tell the taps each attempt's request once its credential's headers are set, the answer's head, and each body chunk or message as it is read. The manager tells them how each executor call ended, and hands the credential errors it records to an error-event hook. Without taps each step costs a branch, and a tap never holds up a send or a stream.
- **The payload hook.** Each executor calls `open_ferry_providers::payload::apply` where upstream applies the config's payload rules, as the last change to a body it sends. It runs the Codex clients' integer pass, `disable-image-generation` and the rules (see [Payload rules](#payload-rules)).
- **The settings.** `commercial-mode`, `logs-max-total-size-mb`, `error-logs-max-files`, `usage-statistics-enabled`, `redis-usage-queue-retention-seconds`, `save-cooldown-status`, `payload` and `disable-image-generation` are read with upstream's defaults and limits, shown by `GET config`, and handed to each part at start and on every reload, including the one after a management write changes them (see [Config writes](#config-writes)). Loading them never writes the config file.
- **The log directory** is resolved as upstream resolves it: `logs` under `WRITABLE_PATH` or `writable_path` if set, else the working directory's `logs` if it exists and can be written to, else `logs` in the auth directory.

Deviations, each also noted in its module:

- **One shared context.** The request's metadata is one `RequestContext` behind an `Arc`, made for every request, where upstream keeps context values and gin keys. It holds no session ID: the manager works out a call's session for session affinity as it picks, and the usage statistics read only a session header the client sent, never one derived.
- **Every executor names itself** to the payload rules and the taps, where upstream names only some: the Codex and xAI ones, and each executor's token count. Only the Codex names change what the rules do.
- **A Codex WebSocket send is announced once, before the connection is made**, as a `GET` of its URL with the `response.create` message as its body and no answer head, then each message read. A send tried again on a new connection isn't announced again; upstream records each, as `WEBSOCKET`. Just before each send, once the connection is up, the taps are also told the request is going out (`Tap::request_sent`), which is where the usage statistics' time to first token starts.
- **The parts are first configured after the credentials load**, so lines logged before that go to standard output, and on a reload the config's changes are logged after the reload's own lines.

### Request logs

The request log is ported (`open_ferry_core::observe::request_log`, with the server's capture layer in `open-ferry-server`'s `request_log`):

- **With `request-log` on**, every logged request gets a file in the log directory, named after its path, the local time and the last eight characters of its ID, as upstream names it: `v1-chat-completions-2026-09-23T101500-1234abcd.log`, with `_1`, `_2` and on for a name taken. The file has upstream's sections: the client's request, its headers and body (a compressed body decoded, see below), the upstream WebSocket timeline, each upstream attempt's request and answer as the taps saw them (`=== API REQUEST n ===`, `=== API RESPONSE n ===`), with an `Error:` line wherever upstream's executors record the attempt's failure, the errors the Responses handlers gave the client over HTTP or a WebSocket (`=== API ERROR RESPONSE ===`), and the answer. A streamed answer is written as it was sent, without the handlers' errors, as upstream writes it.
- **With it off**, a request that fails gets an `error-*.log` file, unless the client left; upstream's rules for what counts are kept (`hasActionableError`). The oldest error logs beyond `error-logs-max-files` are removed. The file has the same sections, but an attempt's answer keeps its body only when its status is an error, and an upstream WebSocket's attempts aren't in it.
- **What is logged**: not a `GET`, unless it is a Responses WebSocket upgrade, nor the management API, nor the dashboard API. A WebSocket session's log is written when it ends, with the attempts of all its turns.
- **`commercial-mode`** turns the request log off, and **`X-CPA-TRACE-ID`** is set on every answer whose request picked a credential before the answer's head: the time it was picked, the credential's index and the request's ID.
- **The routes** `GET request-error-logs`, `request-error-logs/:name` and `request-log-by-id/:id` (v8: `observability/logs/errors`, `errors/:name` and `requests/:id`) list the error logs, send one, and send a request's newest log by its full or short ID, for clients with the management key. They read the log directory the binary resolved at start. The request logger takes a relative directory from the config file's directory instead, as upstream's does, so with a relative log directory and a config file outside the working directory the routes look elsewhere than the logs are, as upstream's do.

Deviations, each also noted in its module:

- **More is kept out of the files.** `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-Management-Key` and `X-Local-Password` are masked along with upstream's sensitive headers, in the answer's headers too, and a credential of one or two bytes is hidden whole, as `...`, where upstream keeps it as it is. Every secret known, however short, is scrubbed from the whole file (bodies, `Error:` lines and `API ERROR RESPONSE` sections included) and from the path the file's name is made from: those each attempt sent (its credential headers after the custom ones, each cookie value, its URL's credentials, its proxy's password and its credential's keys and tokens), those of the client's credential headers, cookies and URL and of the answers' credential headers, and the client's key. The files have mode 0600 on Unix.
- **The `Auth:` line's emails are masked** (`mask::mask_emails`, see [Log files and config changes](#log-files-and-config-changes)): the credential's ID, which for a sign-in is its file's name, and its label, often the account's email, are written such as `auth_id=claude-1a2b3c4d-j***@e***.com.json, label=j***@e***.com`. Upstream writes them as they are. The bodies and headers are left as they were sent, but for the secrets above.
- **A compressed body is decoded or left out**, the client's request and the answer alike. A body sent with `gzip`, `deflate`, `br` or `zstd` (stacked encodings too) is decoded, up to a limit. One that can't be decoded, has another encoding, or decodes past the limit is written as a one-line placeholder (`[ENCODED REQUEST BODY OMITTED: ...]`, `[ENCODED RESPONSE BODY OMITTED: ...]`), never as it came, since a secret compressed in it couldn't be scrubbed; a streamed answer too, where it is compressed. Upstream decodes only a request body's `zstd` and an answer's `gzip`, `deflate`, `br` and `zstd`, writes any other body as it came, writes an answer it can't decode as its compressed bytes followed by a `[DECOMPRESSION ERROR: ...]` line, and cuts a body past its limit with a marker.
- **OAuth callbacks** (a path ending `/callback`) aren't logged, nor is the dashboard API (under `/open-ferry/`), which upstream doesn't have and which, like the management API, carries the management key.
- **Bodies are kept in memory, up to 32 MiB each**, and a line at the end of the file counts what was left out; upstream spills them to temporary files. The answer is kept as it is sent, and the file written once the request is done, by a writer thread of its own, which nothing waits on. When its queue of 1024 is full a log is dropped, and the drops are warned about at most once a minute.
- **With `request-log` on, the client's body is read before the handler runs, up to the server's body limit**, and a longer one is logged cut at the limit with a marker. With it off, the body is kept as the handler reads it, with markers saying what it didn't read; upstream reads a body of up to 1 MiB ahead of the handler.
- **An error log has the provider's answers.** With `request-log` off, each attempt but an upstream WebSocket's gets its `=== API RESPONSE n ===` section: the answer's status and headers, its body when the status is an error, and the attempt's `Error:` line. Upstream's executors record no answer with it off, so its error log's `=== API RESPONSE ===` has only the error the handler gave the client, which is the `=== RESPONSE ===` section here, without the provider's status and headers.
- **The settings are read for each request.** The layer is always installed and checks `commercial-mode` live; upstream installs it only without `commercial-mode`. A request keeps the mode it arrived in.
- **A client that leaves before the answer's head** is logged with status 499; one that leaves during the body, with what was sent.
- **The trace ID is the latest selection's**, taken when the answer's head is ready.
- **Not ported**: the client's own WebSocket timeline (only the upstream one is written), the handshake event and `Stage` line of an upstream WebSocket error, the Codex quota headers' merge into the answer, and the context values that override the bodies logged.
- **Names** also turn `\` into `-`, and keep at most 120 characters of the path. Headers are written sorted, in Go's canonical form.
- **The routes** send a log read whole as `text/plain; charset=utf-8`, with its `Last-Modified`, without Go's type sniffing or range and conditional requests. Error logs with the same change time are listed in name order.
- **The routes refuse a log that is a link**: a symbolic link or other reparse point, anything but a plain file, or a file with another hard link, which may be outside the log directory, answers upstream's 400 for a directory, `invalid log file`. The checks are of the handle the log is then read from. Upstream's follow links.
- **Errors** are worded as Rust words them, for the files.

### Log files and config changes

Ported:

- **The log lines** (`open-ferry`'s `file_log`), in upstream's format: the local time, the request's short ID (`--------` outside a request), the level, where the line was logged, the message and upstream's fields. They go to standard output, or with `logging-to-file` to `main.log` in the log directory, rotated at 10 MB to `main-<time>.log`, every rotation kept. A reload that changes `logging-to-file` or the directory switches the output.
- **The log directory's size limit**: with `logs-max-total-size-mb` positive, its `*.log` and `*.log.gz` files are checked at once and then every minute, and the oldest deleted until they are under the limit, never the `main.log` being written.
- **The access line** (`open-ferry-server`'s `access_log`): the status, the time taken, the client's address, the method and the path, the values of the query parameters that hold a secret masked and their names kept, at info, warn from 400 and error from 500; a health probe answered with a 2xx isn't logged. A request on the AI routes is handled in a span with its ID, so every line logged for it shows the ID, including those logged while its answer's stream is sent: the body is polled in the span again, and the manager's task that forwards a stream keeps it.
- **`GET` and `DELETE logs`** (`open-ferry-management`'s `logs`), at `/v0/management/logs` and `/v8/management/observability/logs`, with the management key. `GET` reads `main.log` and its rotations oldest first: the last `limit` lines, the lines after `after`, or with `cursor` the complete lines written since an earlier answer, followed across rotations. `DELETE` empties `main.log` and removes its rotations.
- **The reads of `usage-statistics-enabled`, `logs-max-total-size-mb` and `error-logs-max-files`** at `/v0/management/<name>`; v8 reads them through `config/*path`. Their `PUT` and `PATCH` save the config (see [Config writes](#config-writes)).
- **The config changes logged on reload** (`open_ferry_core::config::diff`): the lines upstream logs after `config changes detected:`, for every setting open-ferry types. Secrets never show: keys are only said to change, key lists are counted, header values are left out, and a URL shows only its scheme and host. The `config-diff` parity suite compares the lines with upstream's over fixed and seeded random config pairs.

Deviations, each also noted in its module:

- **The lines are written by threads of their own**, one for `main.log` and one for standard output, through bounded queues, so logging never waits on the disk or on a standard output nothing reads; upstream writes each line as it is logged. A line that finds its queue full is dropped and counted, and the count is logged. A switch away from a file returns once the lines queued for it are written and it is closed. At exit, the queued lines are waited for up to a second; any left then are lost.
- **The rotated name's time is local**, where lumberjack's is UTC; the logs routes read it as local, as upstream's do. On Windows, renaming, deleting and truncating are retried while another process has the file open.
- **The size limit's cleaner knows the `main.log` being written by the file it is**, not only by its path, so it keeps it under a name cased otherwise (`MAIN.LOG`, which Windows opens for `main.log`) or linked to it. Upstream keeps it on Windows only because its writer doesn't share deletion.
- **A log directory that can't be made** is logged and the output stays as it was; upstream's start exits.
- **While the TUI runs in standalone mode**, the lines go to its logs tab rather than to standard output, and with `logging-to-file` still to `main.log`. Upstream discards every line then, `main.log`'s too, until a reload changes `logging-to-file`.
- **A line's fields** come from the event and the spans it is in, and a field is quoted when its value was recorded as text.
- **Email addresses are masked in every line** (`mask::mask_emails`), the message's and the fields' alike, whoever logged it, in `main.log`, on standard output and in the TUI's logs tab: an account's email, and the names and paths of the auth files that hold one, such as `C:\auths\claude-john@example.com.json`, written `C:\auths\claude-j***@e***.com.json`. The first character of the local part and of the domain and the domain's last label are kept, so accounts can still be told apart, and so are an auth file's provider prefix and hash (`codex-1a2b3c4d-j***@e***.com-plus.json`). The access line masks them in its path and query, an `@` written `%40` too (`?name=codex-j***%40e***.com-plus.json`). Text without an `@` or `%40` is left alone, and so are versions and hosts that only look like an email (`pkg@1.2.3`, `user@localhost`, `model@20240620`). Upstream logs them as they are.
- **The access line is logged once the response's body is sent or dropped**, and a WebSocket's once its handshake is answered, where gin's comes when the connection closes. The path is written as the client sent it, percent-encoded, except that a key-like query value of one or two bytes is hidden whole, as `...`, where upstream writes it as it is.
- **More of the query is masked.** Besides upstream's key-like names (`key`, and any holding `api-key`, `apikey`, `api_key`, `token` or `secret`), the values of `code`, `state`, `auth` and `sig`, and of any name holding `password`, `passwd`, `credential`, `authorization`, `signature` or `verifier`, are masked, in the access line, the request log's URLs and the secrets scrubbed from it (`mask::is_secret_query_param`). Upstream's gin logger masks only the key-like ones, so its `main.log` holds an OAuth callback's code and state as they came.
- **The logs routes refuse a link.** A `main.log` or rotation that is a symbolic link or other reparse point, isn't a plain file, or has another hard link, which may be outside the log directory, is neither read, emptied nor removed: `GET` and `DELETE` fail with `invalid log file`. The checks are of the handle the file is then read or emptied through, opened without following a link (`O_NOFOLLOW` on Unix, `FILE_FLAG_OPEN_REPARSE_POINT` on Windows), so the file can't be swapped in between; a rotation is checked so, then removed by name, which never reaches a file outside. Upstream's routes follow links. On Windows every reparse point is refused, those a filter such as a cloud-sync client keeps on plain files too.
- **`GET logs` sends its lines as it reads them**, in chunks of about 64 KiB with at most four waiting, so it holds a few chunks and the line being written, where upstream gathers every line it answers (every line of every file without `limit`) before writing any. The body's bytes are upstream's. The files are read twice through the same handles, first to count the lines and find where the answer's are, then to send them, the second time only the files holding the answer's lines, which are all that stay open; a file changed in between gives the lines it then has in that range, never more than counted, with the first read's `line-count`, `latest-timestamp` and `next-cursor`. An answer that fits one chunk is sent whole with its length. A read that fails once the body has started ends it early, where upstream answers 500; one that fails before still answers 500.
- **The logs routes' I/O errors** carry Rust's text, without Go's operation and path.
- **Only the settings open-ferry types have change lines**, and a list or mapping that is missing isn't told from one that is empty. Where two OAuth channel names differ only in case or surrounding spaces, the one sorting last wins.

### Usage statistics

While `usage-statistics-enabled` is on, each executor call makes a usage record (`open_ferry_core::observe::usage`): its tokens, read from the upstream's answer as upstream reads them for Chat Completions, the Responses API and Codex, Claude Messages and Gemini, with upstream's token breakdown; its time to first token, else to its first packet, else to its first byte; its latency, outcome, credential and model, and a warning, each time, when the answer names another model than the one asked for. The records wait in the usage queue, kept while the management API serves requests, for `redis-usage-queue-retention-seconds` (60 unless set, at most an hour). The credential errors the manager records make error events, for the queue's error subscribers. Both settings take effect on reload.

The routes, under `/v0/management` and their v8 names under `/v8/management`, need the management key:

- `GET usage-queue` (`observability/usage/queue`) takes up to `count` records, 1 by default, oldest first. A `count` that isn't a positive integer is a 400 and takes nothing.
- `GET api-key-usage` (`observability/usage/api-keys`) gives each API key credential's successes, failures and recent request buckets, by provider (an OpenAI-compatible provider by its name) and `base-url|key`.

Upstream's own in-memory statistics were removed upstream ([#3200](https://github.com/router-for-me/CLIProxyAPI/issues/3200), below).

Deviations, each also noted in its module:

- **Records are made by a tap on the executor's traffic**, not by the executors. A call's `requested_at` and latency start at its first attempt, and a call that failed before it sent anything is recorded with the credential the manager gave it. A Codex stream's counts are published when the call ends. `reasoning_effort` is always empty: upstream reads it from the translated request, which the tap doesn't see. Gemini stream lines are read without `FilterSSEUsageMetadata`, which only drops usage from lines before the last.
- **`session_id` is only ever a session header the client sent**, as sent, a UUID in lower case. Upstream also derives one from the request and projects one that isn't a UUID onto a version 8 UUID; open-ferry derives one only as a routing key for session affinity, which no record carries. `parent_session_id`, `node_kind`, `is_fork` and `is_compaction` are never written.
- **A stream's reading stops at its terminal line**, not at the blank line after it: an OpenAI-compatible stream's at the `[DONE]` line, where upstream's loop ends at the next line, and Claude's at the `message_stop` data line. Nothing upstream reads between those lines carries counts. A Codex stream's counts were already those of its first terminal event.
- **A call canceled before its executor answered**, while it was still dialing or waiting for the headers, is a failure with status 499 and the body `context canceled` for every stream, as upstream's `TrackFailure` records the error its canceled send returns; upstream's text is the HTTP client's, which names the method and the URL. The report is made before the executor is awaited, so this holds at the first attempt and at the retry after a refresh.
- **A Claude stream dropped before its `message_stop` is a failure with status 499 and the counts it had read**, for any credential. Upstream makes its cancellation error only for an OAuth credential, and records another credential's read cut off by the canceled context as the scanner's error. A stream that read its `message_stop` is a success, as upstream's.
- **A Gemini or Vertex AI stream dropped once it was answered is a success, with the counts it had read.** Upstream's is too when the client went away after the terminal chunk reached it (v8.0.20) or while the executor waited to hand a chunk on, but a failure when the cancel cut off a read before the terminal chunk; a dropped stream here can't tell those apart.
- **A stream the client drops records a failure its executor had already queued**, such as the 502 an `apply_patch` call that couldn't be translated queues right behind its `response.failed` frame: the dropped stream looks, without waiting, at up to 16 items its executor has ready. Upstream records that 502 before it sends anything (`RecordApplyPatchStreamFailure`). A stream dropped before its executor has queued the failure is recorded as a canceled stream is, where upstream's reader, if it is waiting on the body at that moment, reads a failed body, finalizes the translator and records the patch 502.
- **A Codex WebSocket's time to first token starts when its request goes out on the open connection**, as upstream's `StartResponseTTFT` does, not at the dial; the first start wins when a send is tried again.
- **The models a record and the substitution warning name are scrubbed of the credential's secrets**, the one the client asked for and the one the answer served, as a failure's body is: the secrets the attempts sent, the credential's own keys and tokens and the client's key, each however short (see `Policy::Disk`). The served model is whatever the upstream says, and may echo a token it was sent, while a record is served to the management API and can be written to disk and the warning goes to main.log; upstream writes both as they are. The check that the model was substituted still reads the models as they are.
- **Meta's calls are read as Codex's and recorded as `MetaExecutor`.** An Execute is read as a Codex Execute and a Stream as a Codex stream, with upstream's token breakdown of the Responses API. The counts are those of the first terminal event (`response.completed`, `response.incomplete` or, for a stream, `response.done`), where upstream's Meta executor takes a stream's latest `response.completed` or `response.incomplete` and the event its translation found in an Execute's; they differ only if Meta sends more than one.
- **A failure whose error keeps the answer's usage keeps the counts the tap read** of the whole answer, or of the stream as far as it was read: the Meta and xAI executors mark the error when an answer's `apply_patch` call can't be carried over (v8.0.20's `RecordApplyPatchStreamFailureWithUsage` and `StopApplyPatchStreamWithUsage`). Upstream's executors keep what they had observed when the bridge failed, so where the bridge fails at an event before the terminal one of an answer read whole, upstream's record has no counts and this one has the terminal event's.
- **`failed` is the call's own outcome.** Upstream also counts a call failed when the status sent to the client was 400 or more by then.
- **A failure's body is the error's text, scrubbed of every secret the attempts sent, the credential's own keys and tokens (also for a call that failed before it sent anything) and the client's key, each however short**, as the queue is served to the management API and can be written to disk, and the answer's headers are masked as the request log masks them; upstream writes both as they are. An error event's body, and the credential's and the model's status messages, are scrubbed of the credential's keys and tokens, where upstream writes them as they are.
- **Times are in UTC**, in records and error events; upstream writes the local time with its offset. An `execution_id` made here is a version 7 UUID; upstream's is version 4.
- **The queue keeps at most 100,000 records**; past that the oldest are dropped, with a warning at most once a minute. Upstream's grows without bound within its retention.
- **An answer is read as JSON only when it parses whole.** One cut short, nested more than 128 deep or holding a string that isn't UTF-8 gives no counts, no model and no first token, where gjson reads what it can. A key given twice reads as its last value, where gjson reads the first, and an object or array read as text, such as a service tier, is its compact JSON.
- **Records keep the client's key and the credential's account in clear**, as upstream's do; only the management API serves them.
- **The Codex image generation tool's record** (`publishCodexImageToolUsage`, a3b77566), made after a Codex HTTP call's own when its terminal event has `response.tool_usage.image_gen` counts that aren't all zero, names the model of the request's first `image_generation` tool as it was sent, after the payload rules; upstream reads the body before its payload finalizer. It is published when the call ends, right after the call's own record, where upstream publishes both at the event. Its execution ID is its own, a version 7 UUID.
- **Not ported:** Antigravity's usage parsers, the session hierarchy, the credits markers, the SDK's usage plugins beyond the queue, Home mode's skipping of the error events, and the queue over RESP (below). Upstream's `503 core auth manager unavailable` can't happen here.

### Payload rules

The config's `payload` rules (`default`, `default-raw`, `override`, `override-raw` and `filter`) and `disable-image-generation` are ported from upstream's `internal/runtime/executor/helps/payload_helpers.go` into `open_ferry_providers::payload`. The Claude, Codex (HTTP and WebSocket), Gemini, Gemini Interactions, Vertex AI, Meta, OpenAI-compatible and xAI (HTTP and WebSocket) executors call `payload::apply` once for each request they send, as the last change to its body, where upstream applies the rules at its final barrier (`NewPayloadFinalizer` in `helps/payload_finalizer.go`, and `ApplyPayloadConfigWithTrackedPathsForExecutor`). The rules come after the translation and every built-in change, so a rule's conditions see the body as it is sent, and nothing undoes what a rule wrote or removed: an xAI rule's `stop` is sent, and so is a compact request's rule's `top_k`. Only a WebSocket message's `type`, a Claude body's `betas` moving to its header, and serialization follow. A token count's body has the rules applied too, last of all. In order, `payload::apply`:

1. declares a Codex client's whole-number tool parameters `integer` again, unless the body goes to a Codex executor. This is the Codex clients' integer pass, which each executor used to call on its own;
2. with `disable-image-generation` (`true`, or `chat` outside the images endpoints), takes the built-in `image_generation` tool out of `tools`, and removes a `tool_choice` that picks it, so that a rule can put it back;
3. writes the defaults, each only where the client's request lacks the path, the first rule to write a path winning;
4. writes the overrides, the last rule to write a path winning;
5. removes the filters' paths.

**Image and video bodies.** The image and video executors apply the rules with `payload::apply_media` (upstream's `ApplyMediaPayloadConfig` in `helps/payload_media.go`), to a JSON body or a `multipart/form-data` form. The rules see a form as a JSON object, its view: each field a string, each file an object of its `filename`, its `content_type` and its `data` in standard base64, and a name sent more than once an array of its values. A view no rule changes sends the form as it came, byte for byte, with its own content type; a changed view is written as a new form with a new random boundary, a file for each object with a `filename` (a `data` that isn't base64 fails with upstream's `multipart payload <field>: illegal base64 data at input byte N`) and a field holding gjson's `String()` of anything else. The rules have no root, and their defaults check the client's request in its own view, untranslated. A body with a form's content type that doesn't read as one fails with Go's error. Deviations: a form is written back with its fields in name order, then any a rule added, where upstream's map gives a random order; a body that is neither JSON nor a form is sent as it came, where upstream runs sjson on its bytes; whether a view changed is judged on its value, where upstream compares sjson's text; and a changed JSON body is written compactly, as every executor here writes one.

A rule applies when one of its models matches either the model sent upstream or the one the client named, with or without its thinking suffix. That entry's `protocol`, `from-protocol`, `headers` and its `match`, `not-match`, `exist` and `not-exist` conditions must also hold. Paths are gjson and sjson paths under the executor's root, and a `#(query)` key stands for each array item the query matches. The rules are compiled once per config load and shared. The binary installs them with each config it loads, so a reload takes effect on the next request.

**What a rule may write.** A rule writes only the literal value the operator configured, the same on every request. The operator may write identity-shaped fields that way, such as `metadata.user_id`, `user`, `safety_identifier` or `prompt_cache_key`. open-ferry never generates or derives a value for them, and it doesn't port the OpenAI-compatible executor's `prompt_cache_key` derivation (`applyPromptCacheKey`). A rule's `headers` are a read-only gate on whether it applies. No rule writes a header, and none will.

A rule can write any field of a body, and that includes a Claude body's `betas`. The Claude executor reads the body once the rules have run, taking `betas` out of it and sending them in the `anthropic-beta` header, merged with the client's own. A `betas` that a rule wrote is therefore handled exactly as one the client sent: upstream does the same (`extractAndRemoveBetas` runs after its final barrier), and nothing filters either one's betas. The operator who writes the rule chooses them, as they choose any other value. A test pins this.

The `Debug` output of a call and of the compiled rules shows header names and paths, and only the kind and size of a value, never what a header, param or condition holds, since any of them can be a credential.

The rule engine ports the parts of gjson v1.18.0 (`Get`, with wildcards, projections and `#(...)` queries), sjson v1.2.5 (`SetBytes`, `SetRawBytes`, `DeleteBytes`) and match v1.1.1 (`MatchLimit`) that upstream's payload rules use. All three are by Josh Baker and MIT licensed; see [licenses/gjson-LICENSE](licenses/gjson-LICENSE), [licenses/sjson-LICENSE](licenses/sjson-LICENSE) and [licenses/match-LICENSE](licenses/match-LICENSE).

Deviations, each also noted in its module:

- **Rules come from the config last installed**, where upstream reads each executor's own config. A reload that changes only the payload rules re-registers the Codex, Meta and xAI executors but not the others. The rules still reach every executor, since all of them read the installed rules.
- **A rule's params apply in the order the file gives them.** Upstream iterates a Go map, in random order. The order only shows when two params of one rule add keys to the same object.
- **A value that can't be written is dropped at load**, with a warning naming the section, the rule and the path but never the value. Upstream skips it on each request, except a NaN or infinite float, which it writes, leaving the body invalid JSON. A raw value that isn't JSON drops its whole rule, as upstream's config check does.
- **A write that would pad an array with more than 1,024 `null`s is refused**, where sjson writes them all. A refused write changes nothing, as in sjson, which returns the error and the body it was given.

- **A param to write whose path has more than 64 keys is dropped at load**, with a warning naming the section, the rule and the number of keys, and the rest of the rule is kept. Upstream builds a value as deep as the path, and one 2,000 levels deep overflows the stack of a thread that builds, writes or drops it. A `filter` path isn't limited, since it removes only what a body has. (YAML reads no implicit key of more than 1,024 characters, so an operator needs an explicit `?` key to reach the limit.)

- **Some gjson and sjson syntax isn't read**: modifiers, literals, multipaths, JSON lines, pipes, and a path into a string holding JSON. Some paths that upstream writes to the wrong place change nothing instead: a projection inside another, a count, or a list reached through a `#(query)` with a path after it.
- **The client's request is translated for the defaults' check only when a default needs it**, where upstream translates it on every call.
- **The tracked paths are reported but unused.** Upstream's Claude executor asks which of `context_management`, `fallbacks`, `thinking.display` and `diagnostics` a rule touched, for its cloaking and diagnostics, which aren't ported.

Tests: upstream's `payload_helpers_codex_integer_test.go`, `payload_helpers_disable_image_generation_test.go`, `payload_mutations_test.go` and `payload_finalizer_test.go` are ported, along with the Gemini and OpenAI-compatible executors' payload tests and those of `payload_barrier_test.go` and `payload_review_test.go` for the executors that are ported. The tests that are dropped are listed, with reasons, in `crates/open-ferry-providers/src/payload/tests.rs`. The `payload` parity suite runs `ApplyPayloadConfigWithTrackedPathsForExecutor` on fixed cases, covering upstream's test scenarios and each feature's edges, and on generated ones.

### Saved cooldowns and quota fetches

Ported: the cooldown state store (`open-ferry-core::manager::cooldown_store`, upstream's `FileCooldownStateStore`, `RestoreCooldownStates` and `persistCooldownStates`), and `POST /v0/management/quota/fetch` with a credential's declarative quota probe (`open-ferry-management::quota_fetch`, upstream's `FetchCredentialQuota` and `executeQuotaProbe`).

While `save-cooldown-status` is on, the credentials' cooldowns are saved to `.cds` files beside their auth files, and those that haven't run out are put back when the store is turned on. Where the store differs from upstream:

- **Only the file store is ported**: no token store backend's, Postgres or Home.
- **Saves are debounced on a background thread**, which writes with the manager's lock released, so picking a credential never waits for the disk; a save that would write what was last written is skipped. Upstream saves on the caller's goroutine after each change to that credential's records. The binary saves once more as it shuts down.
- **A save that fails is not forgotten**: the store stays marked as unsaved, the worker tries again after the debounce doubled for each failure in a row (up to a minute), and the save at shutdown tries once more even if nothing has changed since. Upstream saves only on a change, so a failed save is made again when something else changes.
- **Cooldowns are restored when the store is turned on or moves** to another auth directory, not on every reload, as a reload here keeps the credentials' state. A credential-wide cooldown other than a quota, which a reload's update drops as upstream's does, stays dropped where upstream's next restore puts it back.
- **A restore doesn't put back what a credential holds newer**: a credential-wide record is applied only if its time is later than that of the cooldown the credential already held, so a fresh cooldown keeps its deadline and time against an older record that runs out sooner, and a model's record isn't applied over a state a later result cleared (against a cooldown it is merged, as upstream merges it). Upstream applies a credential-wide record whatever the credential holds. A credential whose own cooldown a success cleared looks like one that never had one, as the manager keeps no time for the clear, so a record for it is applied.
- **Turning the setting off leaves the files as they are**; upstream saves to them once more.
- **Moving the auth directory loses the saved cooldowns** of the files in both directories: the old directory's credentials are dropped before the store moves, and the new one's arrive after it has restored.
- **Only `.cds` files are ever made or removed**: temporary files end in `.tmp.cds` (upstream's in `.tmp`), and symbolic links are skipped. On Windows, a rename or removal refused for a moment is tried three more times.
- **Nothing is written or removed through a link**: before a save writes a file, or removes a stale one, each directory from the auth directory down to the file's is looked at without being followed, and a symbolic link or Windows junction there refuses it; the file's real directory must also lie under the auth directory's real path. The missing directories are made one at a time. A refused file is skipped with a warning and the others are saved; upstream follows the link and writes outside the auth directory. The auth directory itself may be a link.
- **A `.cds` file keeps none of its credential's secrets**: its free text, the `reason`, the quota's `reason` and the error's `code` and `message`, of the credential's record and of each model's, is scrubbed before the file is written. The credential's own keys and tokens, its credential headers and each cookie value among them, and its proxy's password, however short, become `[redacted]`. Upstream writes them as they came, so an upstream that quotes a key or cookie it was sent ("Bad cookie: session=...") leaves it in the file.
- **A `.cds` file is read only up to 4 MiB and restores at most 10,000 records**; a file over either is skipped with a warning and the others are loaded, and the next save replaces or removes it. Upstream reads a file whole, of any size, and restores every record in it.
- **Times are written in UTC**; a record with a time Go can't write is left out, where upstream's save fails.
- **A record can end with open-ferry's `open_ferry_quota_check`**: the quota rest `routing.quota.check-after` capped under that cooldown, with its `wait_seconds`, `check_at` and `reset_at`, so a restart keeps its doubling. It is written only while the cap is on. Upstream's decoder ignores the key; open-ferry's ignores one that isn't an object with a positive `wait_seconds` and both times, and reads the rest of the record.

A credential whose metadata holds a `quota_probe` with a `url` is probed as upstream probes it: its method, data and headers, with `$TOKEN$` replaced by the credential's token, and the answer read from the response by the probe's `mapping` or in the answer's own shape, with its `summary`. Where the fetch differs from upstream:

- **There is no plugin host**, so only the declarative probe answers; `plugin_id` and `provider` are ignored, and without a probe the answer is 501.
- **The probe never names the client**: a `User-Agent`, `X-App`, `Originator`, session or similar ID, `X-Stainless-*`, `X-Goog-Api-Client`, `X-Client-Id`, `X-Xai-Token-Auth`, `X-Msh-*` or `X-Grok-Client-*` header it gives is skipped with a warning, and the user agent is `open-ferry/<version>`. `Accept: */*` is sent, as `api-call` sends it.
- **The token is never logged or shown**: in a failure's reason, the upstream's body it quotes included, and in the text of a successful answer (a plan, a tier, a window and so on), it is written `$TOKEN$`; upstream shows it in both. It is found in any case of letter, and as a URL or JSON writes it, each character as itself, percent-encoded, or with a JSON escape (`\"`, `\uXXXX`), so a token with a quote or a backslash is found in a JSON error body. Tokens are never refreshed or minted, as in `api-call`.
- **A request and reading its response have a minute**, and a body over 16 MiB fails; upstream's client has no limit. A failed request's reason is this port's client's, without Go's `Get "<url>": ` before it.
- **A header value outside ASCII fails the request.** Headers are applied in the credential file's order and invalid ones reported in the order of their names, where upstream's order is random.
- **Paths are read as gjson reads them**, except that a wildcard, pipe, query, modifier, literal, sub-selector or `..` finds nothing.
- **Of several `summary` members in other cases, the first by name is read**; an RFC 850 `Date`'s zone never moves the time; and the request body is read as the management API reads others (413 over 16 MiB).

## The TUI

`open-ferry -tui` runs the terminal management UI, `open-ferry-tui`, a port of upstream's `internal/tui` from Bubble Tea to ratatui and crossterm. Like upstream's, it is a client of the management API. On its own it signs in to a server already running: at `-management-base-url`, else the config's `management.base-url`, else open-ferry's `management.separate-address`, else 127.0.0.1 at the config's port, with `-password` or else the key typed at its prompt. With `-standalone` it runs the server in the background with a local management password, `-password` or else one made up, and signs in with that once the server answers a config request; its logs tab then shows the server's log lines as they are written. When the TUI ends, so does the server.

Its tabs (dashboard, config, auth files, API keys, OAuth and logs), key bindings and text, in English and Chinese (`L` switches), are upstream's. Its views are built as upstream's lipgloss views are and drawn as Bubble Tea draws them, so a screen matches upstream's cell for cell: the tests drive the app through each tab's key paths against a loopback management server, draw it on ratatui's test backend and compare it with the screens upstream's TUI showed for the same steps (`crates/open-ferry-tui/testdata/screens`).

As upstream's, standalone mode needs a management key in the config or `MANAGEMENT_PASSWORD`: without one, the server refuses every request with "remote management key not set", the TUI's readiness check among them, and the TUI doesn't start. The config tab's changes and the access key changes on the keys tab use the management API's write routes, which answer the empty 404 until they are ported (see [Not ported](#not-ported)); the tab shows the error.

Deviations, each also noted in its module:

- **The views are drawn into a ratatui buffer** the size of the terminal: their last lines that fit, each cut to the width, as Bubble Tea's renderer shows a view. Escape sequences other than SGR draw nothing; the views carry no others. A combining mark is measured with the letter before it, where x/ansi splits it off an ASCII letter; the width is the same.
- **Colours are always written in 24-bit**, or 256-colour for those upstream gives as numbers, as lipgloss writes them on a true-colour terminal. lipgloss writes fewer colours, or none, on a terminal that supports fewer.
- **Keys come from crossterm**, so a terminal may report a few combinations otherwise than Bubble Tea's reader; the keys the TUI binds are named as Bubble Tea names them.
- **The text input's cursor doesn't blink**, and Ctrl+V does nothing (text the terminal pastes still goes in); upstream's blinks and reads the system clipboard on Ctrl+V. **Copying an access key** (`c`) asks the terminal to set the clipboard (OSC 52), which works over SSH; upstream writes to the system clipboard itself.
- **The language belongs to the app**, starting in English, rather than to the process.
- **Commands still running when the TUI quits are dropped**, where Bubble Tea's goroutines run on.
- **Text is cut by characters.** Names, emails, masked keys and the sign-in URL are cut and wrapped by characters, where upstream counts bytes and can split a character; the two agree on ASCII.
- **Control characters are taken out of what the server sends**, every string of its answers, error text and the standalone server's log lines, other than newlines (tabs become spaces), so a server or a client it logs can't write escape sequences to the terminal. Upstream shows them as they come.
- **An answer over 32 MiB is an error**, where upstream reads any answer whole.
- **A sign-in's poll stops once the sign-in is cancelled or another starts**, where upstream's keeps asking the server until the old sign-in ends or times out; and a sign-in the server says expires in over a day is polled for a day, where upstream's timeout can overflow and panic.
- **Inputs upstream panics on do nothing or are guarded:** Enter on a config edit whose setting has gone, Alt+Delete or Alt+D at the second-to-last character (which deletes the last), a negative width for a heading's rule, and, with no client, as upstream's tests make the OAuth tab, starting a sign-in, polling and submitting a callback URL.
- **The standalone server's log hook holds one line at a capacity of 0**, where upstream's unbuffered channel drops every line no one is waiting for. It is made with 2000, as upstream's.
- **Errors' text.** Transport errors read `Get "<url>": <cause>` as Go's do, but the cause is the one this HTTP stack gives; JSON errors are worded as serde_json words them, except type mismatches, which read as Go's. A base URL other than a loopback one uses the environment's proxy as reqwest reads it.
- **The password made up for standalone mode is `tui-` and 128 random bits** in hex. Upstream's is `tui-`, the process ID and the time in nanoseconds, which another local process could guess.
- **A config port that isn't a TCP port fails the readiness check at once**, where upstream asks 30 times.
- **With open-ferry's `management.separate-address`**, the TUI on its own connects to that address after `-management-base-url` and `management.base-url`, and with `-standalone` waits for the server it starts there (`wait_ready_at`), as the management API is served only there ([Added in open-ferry: a management address of its own](#added-in-open-ferry-a-management-address-of-its-own)). Upstream has no such setting.
- **The TUI is handed what opens a URL**, the binary's `browser`, rather than opening the browser itself, and it writes to standard output only.

Not ported:

- The OAuth tab's Antigravity, Kimi (both sites), xAI and Meta sign-ins: open-ferry doesn't sign in to them.
- `SetLocale`, `CurrentLocale`, `formatKV`, `formatLargeNumber` and `truncate`, the client's `GetConfigYAML`, `PutConfigYAML`, `RefreshAllAuthFiles`, `GetDebug` and `DeleteField`, and the styles upstream defines but never uses: nothing in the TUI calls them.
- The text input's suggestions and validation, and the viewport's mouse wheel and horizontal scrolling: the TUI uses none of them.
- The log hook's `SetFormatter` and `Levels`: the server hands it each line formatted, at every level.

## Added in open-ferry: the dashboard

Upstream's control panel is a single web page, from its Cli-Proxy-API-Management-Center project, which it downloads from a GitHub release into its static directory, keeps up to date in the background, and serves at `/management.html`. open-ferry has a dashboard of its own instead (`open-ferry-dashboard`): a web app built into the binary, an API of its own beside the management API, and a usage ledger behind that API. `docs/dashboard-api.md` is the contract between the server and the app.

What open-ferry adds:

- **The app**, at `/dashboard/`: a single-page app in TypeScript and React, from `dashboard/` at the repository root, which Vite builds into `dashboard/dist` and the crate's `build.rs` embeds at compile time. A path below `/dashboard/` that isn't one of its files answers `index.html`, for the app's own routes, except below `/dashboard/assets/`, where it is a 404. The files under `assets/` are named by their content and cached for good; every other answer is `no-cache`. A binary built without the app (without Node.js, or before `npm run build`) serves a page saying so and how to build it, and a build with `OPEN_FERRY_REQUIRE_DASHBOARD=1`, as a release's is, fails instead. The app is served without a key: it asks for the management key and sends it with its API calls.
- **Security headers.** Every answer from the app's paths, `/management.html` and the dashboard API carries a Content Security Policy that allows nothing from elsewhere, nothing inline and no framing, with `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY`. Nothing is fetched from outside the binary.
- **The dashboard API**, under `/open-ferry/api/v1/`, a prefix upstream doesn't use, so the management API's paths stay upstream's. It serves usage totals, groups and a time series, the calls themselves, the ledger's state and settings, deleting its records, and prices per model; a bounded search of the request logs, reading a log in pieces and downloading one byte for byte; and what the app needs for client setup, the proxy's base URLs and the models each route serves. It checks access with the management API's own code: the key in the same header forms, the local management password from 127.0.0.1 and ::1, the local and remote rule, and one record of failed attempts toward the same ban. Its errors are `{"error": "<code>", "message": "<text>"}`.
- **The usage ledger**, `open-ferry-usage.sqlite3` in the log directory, a SQLite file (through `rusqlite`, with SQLite built in). It observes the usage records the server makes while `usage-statistics-enabled` is on, without taking them from the usage queue, and a thread of its own writes them, so no request waits on the disk; when it falls behind, records are dropped and counted. A row is one upstream call. It holds no prompt or answer text, the client's key only masked and as an HMAC-SHA256 under the ledger's own secret, and the credential by its ID, index and label. Rows are kept for 90 days, and at most a million, by default. Those settings, and the prices that costs are estimated from at query time, live in the ledger, not in `config.yaml`; no prices are shipped. A ledger of a newer schema than the binary knows is left alone, and the usage routes say it is unavailable.

Where it differs from upstream's control panel, each also noted in its module:

- **`/management.html` sends the browser to `/dashboard/`**, with a 302 that keeps the query, so upstream's safe-mode link, `/management.html?safe-mode=configure`, opens the dashboard's API key setup. Upstream serves its panel's page from its static directory, downloading it when it's missing from the GitHub repository that `management.panel-github-repository` names, which is read and ignored here: nothing is downloaded. As upstream's, it answers an empty 404 while `management.disable-control-panel` is set, and so do the app's paths.
- **A client the management API refuses for its address gets the same refusal** at `/management.html` and the app's paths: one that isn't 127.0.0.1 or ::1 while remote management isn't allowed, or one that is banned. Upstream serves its panel to anyone.
- **Safe mode has no warning page.** While `api-keys` holds one of the example keys, upstream answers `GET` and `HEAD` of `/`, and of `/management.html` without `?safe-mode=configure`, with a page that warns about them and links to the panel. Here safe mode only shuts the proxy routes, with upstream's 403 and message, which links to `/management.html?safe-mode=configure`; `/` names this port as always, and `/management.html` goes to the dashboard. `HEAD /management.html` is a 404, as upstream's is outside safe mode.
- **Home mode isn't ported**, so it doesn't hide the dashboard, as it hides upstream's panel.
- **The ledger is opened at start**, in the log directory, whether or not `usage-statistics-enabled` is on, so the directory and the file are made then; upstream makes the log directory only to write a log there. The directory is made before the server serves, and the file on the ledger's own thread while it starts to: the records made meanwhile wait for it, and so do the usage routes. A ledger that can't be opened leaves the server running, and the usage routes say why. At shutdown, once the server has stopped, the ledger has up to 10 seconds to write the records it was sent.
- **The dashboard API isn't request-logged**, as the management API isn't (see [Request logs](#request-logs)).
- **The dashboard can have an address of its own**, with the management API, apart from the proxy's port: see [Added in open-ferry: a management address of its own](#added-in-open-ferry-a-management-address-of-its-own).

Tests: the "management button query opens control panel" case of upstream's `TestExampleAPIKeySafeModeShowsWarningAndKeepsManagement` is ported, with the redirect in place of the panel. Its warning page cases, the Home mode case of `TestHomeEnabledHidesManagementEndpointsAndControlPanel` and `internal/managementasset`'s tests aren't, as what they test isn't ported.

## Added in open-ferry: claude-cli

Upstream has no counterpart. `claude-cli` serves Claude models through the user's own installed Claude Code, run once per request as `claude -p` with JSON lines in and out. Anthropic's terms forbid a third-party tool to sign in to a Claude subscription and call the API with its tokens, which is what the Claude sign-in does, but allow a user to sign in to the unmodified Claude Code with their own subscription ([docs/claude-subscription.md](docs/claude-subscription.md)). So Claude Code signs itself in and makes every request to Anthropic; open-ferry reads no credential, stores none, runs no sign-in and sends no request for this provider.

- **The config's `claude-cli` list** (`config::ClaudeCli`), at the top level in both layouts: each entry's name, command, config directory (`CLAUDE_CONFIG_DIR`), system prompt mode (`replace` or `append`), concurrency, timeout, and the prefix, models, excluded models, priority, weight and disabled switch an API key entry has. Saving, v8 edits, reload change lines and the management config read know it, and `config.example.yaml` has a commented example.
- **A credential for each enabled entry** (`auth::synthesizer::claude_cli`), for the `claude-cli` provider, with a stable ID from the entry's name and config directory. It holds no secret, only how to run Claude Code. Its models are the built-in Claude ones, or the entry's, with model aliases, quota readings and usage handled as Claude's.
- **The executor** (`open-ferry-providers`, `claude_cli`). A request is translated to Claude Messages as the Claude executor does, then given to Claude Code as one user message: a conversation of several turns goes as a transcript in that message. Client tools are refused with a 400, and sampling settings are dropped. Claude Code runs with its tools, MCP servers, slash commands and session files off, for one turn, in an empty directory of the entry's own, with every `ANTHROPIC_*` and `CLAUDE*` variable and `MAX_THINKING_TOKENS` removed from its environment; `CLAUDE_CODE_OAUTH_TOKEN` and `CLAUDE_CONFIG_DIR` stay only for an entry without a config directory. Its stream events become a Claude SSE stream, translated to the client's format, or one answer; thinking the client didn't ask for is dropped, and thinking it asked for has its signature but no text, as Claude Code gives none. Its rate-limit events become Anthropic's unified rate-limit headers, which feed quota readings, and its errors become the API's statuses, with sign-in, billing, rate-limit and unknown-model errors stopping it at once. The process is ended when the client goes away or the entry's timeout passes. Token counts answer 501.
- **A version check**: at start, and when a reload changes the list, each entry's `claude --version` is run in the background, with a warning when Claude Code is older than 2.1.259 or can't be run.
- **Two dashboard API routes** ([docs/dashboard-api.md](docs/dashboard-api.md#claude-cli)): `GET /open-ferry/api/v1/claude-cli/entries`, the entries with their credentials as the management API's `auth-files` would list them, which it leaves out as made from the config, and their last errors; and `GET /open-ferry/api/v1/claude-cli/auth-status?name=<entry>`, which runs the entry's `claude auth status --json` and answers only whether it is signed in and how. The dashboard's Credentials page shows the entries with them. The management API's paths stay upstream's.

Tests: `tools/fake-claude-cli` builds `fake-claude`, a stand-in for Claude Code that records how it was run and prints canned output, and its tests run the executor against it. No test runs the real Claude Code.

## Added in open-ferry: `init`, `check` and `service`

Upstream has no counterpart. `open-ferry init` writes a starting config, `open-ferry check` looks over a setup before a start, and `open-ferry service` installs open-ferry as a background service ([docs/cli.md](docs/cli.md)).

- **`init`** (`init`, `installed`) writes the built-in `config.example.yaml` with every comment kept and four settings changed: one new client key in place of the example `api-keys`, a new `management.secret-key`, `server.host` set to `127.0.0.1` (or `-host`) and `server.port` to `-port` when given. The keys come from the operating system's random number generator: the client key is `sk-` and 32 bytes in URL-safe base64, as the dashboard makes them, and the management key is 32 bytes in hex. The file goes to `-config`, else the installed config path, `${XDG_CONFIG_HOME:-~/.config}/open-ferry/config.yaml` or `%APPDATA%\open-ferry\config.yaml`; the server doesn't read that path itself. It is written through the config writer (`config::save::write_as_is`), so it must load first, is written atomically, is 0600 on Unix, and an existing file, replaced only with `-force`, is kept as `<file name>.bak`. On Windows the file keeps the permissions it inherits from its folder. The keys are printed once.
- **`check`** (`check`) finds the config as the server does, loads it with the server's loader, and reports a line for each finding, or one JSON object with `-json`: safe mode, the client and management keys, the auth directory and each credential file as the server reads it (bad ones named, never shown), TLS, whether the address is taken (by connecting to loopback, never by binding), the management address when `management.separate-address` sets one ([Added in open-ferry: a management address of its own](#added-in-open-ferry-a-management-address-of-its-own)), the dashboard app, the system time against the build date and the credentials' times, and each `claude-cli` entry's `claude --version`. It exits with 0, 1 when a finding is an error, or 2 when it couldn't check. It writes nothing and makes no network call beyond loopback.
- **`service`** (`os_service`) installs open-ferry as a service of the system's service manager (`install`), removes what that made (`uninstall`) and shows it (`status`); `-dry-run` prints what it would write and run. The service runs the binary that ran `install`, by its full path, with `-config` and the config's full path (the installed config path by default), in the config's directory, and is started again when it fails. By default it is the user's: a systemd user unit, a launchd agent, or on Windows a scheduled task at their logon, which runs `open-ferry service run` to keep the server running with no window and its output in `service.log`. With `-system` it is a systemd system unit, a launchd daemon or a Windows service run as LocalSystem (through the `windows-service` crate), which needs root or an administrator and refuses an auth directory under `~` and a binary or config that anyone but root or the administrators can change.

Where it differs from upstream:

- **Subcommands.** Upstream has no subcommands: it parses its flags, ignores the arguments after them, and serves, so `cli-proxy-api init` starts the server. Here `init`, `check` or `service` as the first argument runs that subcommand, with its own flags. With a flag first, the command line is read as upstream reads it, so `open-ferry -config x.yaml init` still serves.

Tests: none are upstream's. The subcommands' tests use temporary directories and ports on 127.0.0.1 that nothing listens on, and check the keys' shape without printing them. `service`'s tests run every command and file change through a recording fake, so none reaches a real service manager, and check the definitions it writes against their text.

## Added in open-ferry: commands and an MCP server for agents

Upstream has no counterpart. `open-ferry status`, `config`, `keys`, `credentials` and `clients` look at and change a setup, and `open-ferry mcp` serves the same commands as the tools of a Model Context Protocol server ([docs/cli.md](docs/cli.md#looking-at-and-changing-a-setup), [docs/mcp.md](docs/mcp.md)). They are `open-ferry`'s `agent` module: one action per command, which the command line and the MCP server both call, with the same inputs and the same JSON.

- **The server** (`agent::target`): the config's management address, `management.separate-address`, else `server.host` and `server.port`, tried on loopback only. The management key is the config's `management.secret-key` when it is plain, else `MANAGEMENT_PASSWORD`, else a key file's first line, never an argument. They call the management API with the TUI's client (`open_ferry_tui::ManagementClient`), and check it with `GET /v0/management/debug`.
- **Changes** (`agent::change`): with a server reached, through its routes: `PUT`, `PATCH` and `DELETE` of `/v8/management/config/<path>` and `PUT /v8/management/config.yaml` for settings, and `/v0/management/api-keys` for a client key, which the server saves under its write lock. With none, in the file, with `open_ferry_core::config::v8_edit::edit_v8`, the v8 routes' writer. Either way the change is first made on a copy (`v8_edit::preview_v8`, open-ferry's own) and compared with the file, to report it and to see whether it needs a confirmation. Paths are checked against `v8_edit::known_v8_paths`.
- **Undo**: the dashboard API's `POST /open-ferry/api/v1/config/undo`, open-ferry's own, swaps the config and its `.bak` under the management write lock and reloads the config ([docs/dashboard-api.md](docs/dashboard-api.md#post-open-ferryapiv1configundo)). With no server, the command swaps them itself. Either way it refuses, unless forced, when the file isn't what the last write recorded in `<config>.sha256`, and refuses when the file or backup isn't the one the caller previewed (the SHA-256s it sends).
- **Credentials** go through upstream's routes: `auth-files`, `auth-files/status`, `reset-quota`, the deletion of an `auth-files` entry, and the logins, `codex-auth-url`, `anthropic-auth-url`, `get-auth-status` and `oauth-session`; and the dashboard API's `claude-cli/entries`.
- **Guardrails** (`agent::guard`) and **masking** (`agent::mask`): deleting, revealing, replacing the whole config and changing a sensitive setting need a confirmation; client keys are masked as the dashboard's usage masks them (`open_ferry_dashboard::mask_client_key`), headers, URLs and email addresses as the request log masks them, and every secret of the setup is then scrubbed from the output.
- **The MCP server** (`agent::mcp`) uses `rmcp`, the official Rust SDK, on standard input and output: one tool per command, with annotations, the command's JSON as structured content, and `docs/agents.md` and the masked config as resources.

Where it differs from upstream:

- **More subcommands.** As with `init`, `check` and `service`, each of these as the first argument runs that command, where upstream would serve. With a flag first, the command line is read as upstream reads it.

Tests: none are upstream's. They write configs in temporary directories, serve the management and dashboard APIs in-process on 127.0.0.1 ports the system picks with dummy keys, make a closed port with a bound `TcpSocket` that doesn't listen, and talk to the MCP server over in-memory pipes and to `open-ferry mcp` as a child process.

## Added in open-ferry: a management address of its own

Upstream has no counterpart: its management API and control panel are served on the proxy's port, beside the proxy's routes. open-ferry's `management.separate-address` (`remote-management.separate-address` in the legacy layout) serves the management API, the dashboard and the dashboard API on a listener of their own, so the proxy's port doesn't have those routes at all. It is a `host:port` string, empty by default, which leaves everything on the proxy's port as before: `127.0.0.1:8318`, `[::1]:8318`, `localhost:8318`, or `:8318` for every interface. Loading trims it and refuses a config whose value has no port, a port of 0 or `server.port`'s, an IPv6 address without brackets, or a URL (`config::management_address` in `open-ferry-core`). open-ferry's config writer keeps it, moving it with the other `management` settings when it moves a file to the v8 layout, the v8 edits take it, and a reload logs its change.

**The name** is open-ferry's own: upstream's config has no `separate-address`, and no other management address, at v8.0.15 or v8.0.20. What CLIProxyAPI does with a file that has it, the same at both versions:

- **It loads the file and ignores the key.** `LoadConfig` (`internal/config/config_load.go`) decodes the file with `yaml.Unmarshal`, and `Config.UnmarshalYAML` (`config_v8.go`) flattens the v8 layout and decodes it without `KnownFields`, into a `RemoteManagement` that has no such field; `NormalizeConfigLayout(current, false)` at load leaves the key where it is. So CLIProxyAPI serves its management API on its port, as always.
- **A save of a v8-layout file through its management API turns the key into a comment.** `WriteConfig` (`handlers/management/config_basic.go`), `ConfigV8` (`handlers/management/config_v8.go`) and `SaveConfigPreserveComments` (`config_yaml.go`) run `NormalizeConfigLayout(data, true)` on such a file, whose `commentUnknownV8Fields` moves each key it doesn't know into a comment at the end of the file and logs a warning.
- **`PUT /v8/management/config.yaml` refuses the file.** `ConfigV8` checks it with `ValidateV8Config` first, which decodes with `KnownFields(true)`.

**With the setting** (`service::management_listener` in `open-ferry`):

- **The proxy's port** serves the proxy as before, with `/`, `/healthz`, the keep-alive endpoint and the sign-in callback pages, `/anthropic/callback` and `/codex/callback`, where the management API's callback forwarders send the browser. Every path under `/v0/management` and `/v8/management` answers an empty 404, as while no management key is set (`open_ferry_management::pages_router`); `/dashboard`, the paths below `/dashboard/` and `/management.html` an empty 404, as while `management.disable-control-panel` is set; and every path under `/open-ferry/`, the dashboard API's routes among them, 404 `not_found` ("no such route"), whatever the method, as a path that isn't one of its routes does (`open_ferry_dashboard::Listener::Closed`). Nothing else changes there.
- **The management address** serves the management API (`open_ferry_management::api_router`, every route but the callback pages), the dashboard and the dashboard API (`Listener::Separate`), with the same checks: the management key, `allow-remote` for a client other than 127.0.0.1 and ::1, and the bans, which the two addresses share. Every other path, the proxy's routes, `/` and `/healthz` among them, answers gin's `404 page not found` (`open_ferry_server::router_without_proxy`). It passes through the same request context, logs, CORS and panic handling as the proxy's port.
- **TLS:** both use `server.tls`, the same certificate and key.
- **Start and stop:** the management address is bound right after the proxy's, before either serves, and either failing to bind stops the start with exit code 1 and a message naming the address, such as `failed to start the management server on 127.0.0.1:8318: <error>`. Both stop together, with the same 30 seconds for open requests, and one failing to serve stops both.
- **A change takes a restart**, as one to `host`, `port` or `tls` does; a reload logs that it was ignored. `open-ferry check` says so too.
- **The TUI** (`tui` in `open-ferry`, and `open_ferry_tui::wait_ready_at`): on its own it connects, after `-management-base-url` and `management.base-url`, to the management address, on 127.0.0.1 when that is every interface and with `https` while `tls` is on; with `-standalone`, it waits for the server it starts there.
- **`open-ferry check`** (`check::management`) adds a `management address` finding: an error when something already listens there, found as for the proxy's address, by connecting to loopback; a warning for a host name or an address other than loopback, which it doesn't connect to; otherwise that the management API and the dashboard are served there alone, and that a change takes a restart. It adds a `management access` warning when `allow-remote` doesn't fit the address: an address other machines can connect to (every interface, or one that isn't loopback) while `allow-remote` is off and `MANAGEMENT_PASSWORD` isn't set, since they would be refused; or a loopback address while `allow-remote` is on and `server.trusted-proxies` is empty, since then no other machine can connect and `allow-remote` does nothing. Its `dashboard` finding gives the dashboard's URL at the management address. A port that is `server.port`'s fails the config's load, so `config` reports it.
- **The dashboard API's `client-setup`** says `separate_management: true` when served at the management address, and leaves `management.base-url` out of `base_urls` then, as it is the management address's ([docs/dashboard-api.md](docs/dashboard-api.md#client-setup)).

Tests: none are upstream's. They bind 127.0.0.1 on ports the system picks, and make a closed port with a bound `TcpSocket` that doesn't listen. They check each listener's answer for each route against the set above, the proxy's port against a server with management off (its dashboard API paths against that server's answer to a path that isn't a route), the bind failures' messages, both listeners stopping together and both using TLS, the TUI's default and readiness check, and each `check` finding.

## Added in open-ferry: routing by quota

Upstream has no counterpart. Two routing settings are open-ferry's own ([docs/routing.md](docs/routing.md)):

- **`routing.strategy: quota`** (`manager::quota_rank`) picks among the ready credentials of a priority by the quota windows their provider last reported, as upstream's `quota_signals.go` records them: Claude's (and `claude-cli`'s) 5-hour and 7-day windows, and Codex's primary and secondary ones. `routing.quota.prefer` is `soonest-reset` (the default) or `most-left`, and `routing.quota.reserve-percent` (0 by default) keeps a share of each window back.
  - A window counts while its reset is ahead. A credential with no current window, such as an API key, a provider that sends no quota headers, one not used since the start or one whose windows have all reset, has room, with all of its allowance left.
  - Credentials with room above the reserve in every window come first. Among them, `soonest-reset` takes the binding (fullest) window's earliest reset first and puts those with no reading last; `most-left` takes the most left first, counting no reading as full. When none has room, the one with the most left serves. Ties take turns, as round-robin does.
  - Priority still comes first and a session affinity binding still wins: the strategy is an arm of the scheduler's per-priority pick, its multi-provider pick and the legacy pick that affinity falls back to (`manager::select`). Weights are ignored.
- **`routing.quota.check-after`** (`manager::quota_check`), a Go duration, off by default, caps a quota rest whose provider reset is further away. When the cap is up, one call is let through to check, and while it is in flight no other call picks the credential for that rest. A success ends the rest; another quota answer doubles the wait, never past the provider's reset, after which upstream's rules apply. The rests are kept in a table beside the credentials, and the cooldowns are written as upstream writes them before their times between the check and the reset are brought back to the check. `reset-quota` ends them; `save-cooldown-status` saves them (see [Saved cooldowns](#saved-cooldowns-and-quota-fetches)); `auth-files` shows them as `quota_checks` (see [Listing, API calls and quota](#listing-api-calls-and-quota)).

The config (`config::RoutingQuota`) loads, saves and reloads in both layouts, and the v8 API edits it under `routing.quota`. The management API's config JSON shows it under `routing` as `quota`, left out when nothing in it is set, and `PUT /v0/management/routing/strategy` takes `quota`. A save writes only the keys the config sets.

What upstream does with a config that uses them, at v8.0.15 and v8.0.20 alike:

- **Its loader ignores `routing.quota`**, as it ignores any field it doesn't know, and **runs `strategy: quota` as round-robin**: `normalizedRoutingRuntimeState` maps only the weighted and fill-first names, and `newRoutingSelector` makes a `RoundRobinSelector` for anything else (`sdk/cliproxy/service_config.go`).
- **`PUT /v0/management/routing/strategy` with `quota` answers 400 `invalid strategy`** (`internal/api/handlers/management/config_basic.go`).
- **Its management writes to a config in the v8 layout comment the section out**, with the warning `unrecognized configuration section "..." commented out during v8 migration`: `SaveConfigPreserveComments` (`internal/config/config_yaml.go`) and `WriteConfig` (`internal/api/handlers/management/config_basic.go`) run `NormalizeConfigLayout` with `migrate`, which runs `commentUnknownV8Sections` (`internal/config/config_v8.go`). A v8 write that sets `routing.quota` answers 400 `invalid_config`, since `ValidateV8Config` decodes with known fields only. A legacy-layout config keeps the section through its `/v0/management` writes.

Where it differs from upstream: all of it. There is no parity suite, as upstream has nothing to compare with. The tests (`manager::tests::quota_routing`, `manager::tests::quota_check`, the config's `routing_quota_tests` and the management API's `auth_files_quota_checks`) use credentials with set readings and fake executors in process, with no upstream or socket at all.

## The container image and Compose file

`docker/Dockerfile` and `docker-compose.yml` are ported from upstream's `Dockerfile` and `docker-compose.yml` (MIT). The image keeps upstream's paths, so a Compose file written for upstream's image switches by changing the image ([migration guide](docs/migrating-from-cliproxyapi.md#docker-compose)): the working directory `/CLIProxyAPI`, the config `/CLIProxyAPI/config.yaml`, the template `/CLIProxyAPI/config.example.yaml`, the auth directory `/root/.cli-proxy-api`, the logs `/CLIProxyAPI/logs` and the port 8317.

Where they differ:

- **The image is built from the release's static (musl) binaries, on Alpine**, pinned by digest, for linux/amd64 and linux/arm64. Upstream compiles the source in its image build and runs it on Debian. The binary is `/usr/local/bin/open-ferry`, and `/CLIProxyAPI/CLIProxyAPI` is a link to it, for commands written for upstream's image. The licenses are in `/usr/share/doc/open-ferry`, and the image has OCI labels.
- **The time zone is UTC**, where upstream's image sets `TZ=Asia/Shanghai`. `TZ` still sets it; the zone database comes from Google's distroless static image, pinned by digest.
- **The Compose file** takes the image from `OPEN_FERRY_IMAGE` rather than `CLI_PROXY_IMAGE`, and has no `build:` section, `pull_policy: always`, plugins volume or `DEPLOY`. It publishes only 8317, on 127.0.0.1, with a commented line that publishes 8318, also on 127.0.0.1, for open-ferry's `management.separate-address: ":8318"`; upstream publishes 8317 and the sign-in callback ports 8085, 1455, 54545, 51121 and 11451 on every interface, but open-ferry's callback servers listen on the container's loopback, which a published port doesn't reach.
- **A save with upstream's single-file mount leaves its backup in the container.** A file bind-mounted on its own can't be renamed over, so the config writer writes it in place there, as upstream does ([The config writer](#the-config-writer)), and its backup, `config.yaml.bak`, is written to the container's `/CLIProxyAPI`, not the host. Upstream keeps no backup.

## Checking parity

`tools/parity` runs the same requests and event streams through upstream's Go translators and through ours, then compares the output. It covers every translator ported so far, the config writer, and the quota snapshot kept of response headers. It needs Go and a CLIProxyAPI checkout:

```sh
cargo run --release -p open-ferry-parity -- --upstream ../CLIProxyAPI
```

`--go` picks the Go toolchain. To build upstream as its releases are built, use Go 1.26 (`go install golang.org/dl/go1.26.4@latest`, then `go1.26.4 download`) and pass `--go go1.26.4`.

With `--summary README.md` it also rewrites the summary in the README's [Parity with CLIProxyAPI](README.md#parity-with-cliproxyapi) section. See [tools/parity/README.md](tools/parity/README.md).

## Deliberately not ported

- **Client impersonation:** TLS fingerprinting (uTLS), synthetic user IDs, forged client build fingerprints, related "cloaking" code, and `cmd/fetch_codex_models`, which downloads the Codex client model catalog posing as the Codex CLI. We send each provider's documented OAuth headers and nothing that disguises the client. OpenAI-compatible upstreams get `User-Agent: open-ferry/<version>` rather than upstream's `cli-proxy-openai-compat`.
- **Providers beyond Codex, Claude, Gemini, Gemini Interactions, Vertex AI, Meta (API keys and access tokens only), xAI (API keys only) and OpenAI-compatible upstreams** for now (Antigravity, Gemini CLI, Kimi, Meta's and xAI's sign-in, Devin, AI Studio relay). Their reasoning signatures are recognized, because a conversation can move between providers and each signature must be kept, dropped or replaced before it's replayed.
- **Not yet, but on the [roadmap](ROADMAP.md):** Realtime over WebSocket and WebRTC (v2), the plugin host and store (v3), and cluster mode with CLIProxyAPIHome (v4).
