Healthy account

Response streaming

Sample: a Codex request for gpt-5, with session affinity enabled and an existing binding to account A. Affinity is off by default.

  1. 0 ms
    Accept the request

    The client’s proxy key is checked.

  2. 1 ms
    Keep account A

    The session’s bound account is ready for this model. With no usable binding, priority and the configured strategy choose an account.

  3. 240 ms
    Stream the answer back

    The provider answers through account A; output returns to the coding tool.

Affinity can keep a conversation on a ready account for prompt-cache reuse; it does not guarantee a cache hit.

Quota failover

Recovered through account B

Sample: both Codex accounts serve gpt-5, with no aliases, model pools or pre-token keep-alives. Account A returns HTTP 429 before any output reaches the client.

  1. 0 ms
    Check the client key; choose account A

    Account A is initially ready for the requested model.

  2. 90 ms
    Record the quota failure

    The provider reports that account A’s quota is used up. No output has reached the client.

  3. 92 ms
    Try account B, keeping gpt-5

    Another eligible account is tried within the configured credential limit.

  4. 330 ms
    Return account B’s stream

    The answer arrives through account B.

Two different keys. The client’s proxy key is never sent upstream. The selected account’s provider credentials go to the provider.

Before output only. This recovery does not replay a response after partial output has reached the client.

No account ready

429 · model_cooldown

Sample: Codex account A is in a quota cooldown for gpt-5; account B is disabled. Additional retry rounds and cooldown waiting are disabled for these accounts.

  1. 0 ms
    Check availability

    Account B is excluded. Account A cannot serve this model until its cooldown ends.

  2. 1 ms
    Return the cooldown error

    No upstream attempt is made in this sample. Wait for account A’s reset, or enable an eligible account.

HTTP 429 · sample error body

{
  "error": {
    "code": "model_cooldown",
    "last_upstream_error": "rate_limit_exceeded: quota used up",
    "message": "All credentials for model gpt-5 are cooling down via provider codex (last error: rate_limit_exceeded: quota used up)",
    "model": "gpt-5",
    "provider": "codex",
    "reset_seconds": 60,
    "reset_time": "1m0s"
  }
}

Retry and wait settings change this behavior. The sample disables both; the general routing policy can wait and try another round.

02 / Check the evidence

Read the limits before you switch.

Compatibility you can check

A port with a pinned reference.

Open Ferry is ported from CLIProxyAPI v8.0.38. Differential tests send the same inputs through upstream’s Go code and the Rust port, then compare the outputs. The linked README parity totals were run against v8.0.32.

Supported upstreams include Codex, Claude, Gemini, Vertex AI and OpenAI-compatible providers. Client formats, models and features depend on the upstream and connection type.

Client impersonation, the plugin host, Home/cluster mode and Realtime are not ported. Documented deviations remain.

Performance with the fine print

A benchmark, with its boundaries.

The published run used an Azure Standard_D8s_v6 VM: 8 vCPUs, Intel Xeon Platinum 8573C, in East US, on 2026-10-24.

Both proxies ran in front of the same fake upstream. The workload includes short requests and a coding agent’s long conversation, streamed and unstreamed, in native and translated formats.

It does not measure real providers, TLS, OAuth credentials or WebSockets. The load generator shares the machine; connection limits stopped some CLIProxyAPI load levels early.

03 / Start locally

Build it. Add an account. Connect.

Candidate releases exist to test signed updates. For install scripts, see the README’s Install section.

  1. 01

    Install locally

    You need Rust and a C compiler; some systems also need CMake. This source build runs the proxy without the dashboard app.

    git clone https://github.com/Loft-902-Co-LLC/open-ferry-ai-proxy.git
cd open-ferry-ai-proxy
cargo build --release --locked -p open-ferry

    Put target/release/open-ferry (open-ferry.exe on Windows) on your PATH. Then create a local config:

    open-ferry init

    Run the check and start commands that init prints, with the config path already filled in.

    Full build instructions, including the dashboard ↗
  2. 02

    Add a provider

    With the server running, this command starts a Codex sign-in through the server:

    open-ferry credentials login codex

    API-key providers can be configured using the commented examples in your config. For Claude, read the connection options and limits first.

    Credential commands ↗ · Claude connections ↗
  3. 03

    Connect a tool

    Print the Codex client setup for your config:

    open-ferry clients setup codex

    The command prints a base URL and config snippet, with the client key masked. It does not write the tool’s config. Add the printed snippet to Codex’s config, then start Codex with your client key in the OPEN_FERRY_API_KEY environment variable, as the setup output instructs.

04 / Before you start

Questions people ask.

What carries over from CLIProxyAPI?
The config and auth directory are read in place. open-ferry migrate previews a switch and asks first; open-ferry migrate -undo reverses the recorded switch. Some providers and features do not carry over. Read the migration and undo guide.
Which Claude connections are available?
An Anthropic API key; your installed Claude Code through claude-cli; or the legacy Claude sign-in, which goes against Anthropic’s terms and can get an account limited or suspended. Don’t use it; in testing it also reached only Haiku models. claude-cli does not support client tools or token counting. See Claude connection types and limits.
Where do requests go, and what is kept?
Requests go to the selected upstream. The local usage ledger records calls while enabled, without prompt or answer text and without client keys in clear. Request logs can contain request and answer bodies, with known secrets scrubbed; failures can be logged even when request-log is off. Automatic update checks contact GitHub unless disabled. Read usage records, request logging, configuration and update requests.
Who sets billing and terms?
Your provider’s billing and terms still apply. Whether subscription access through a proxy is allowed depends on those terms. Some users of similar tools have had accounts restricted. Read the terms note and the connection guide before using an account.
How do I report a security problem privately?
Use the repository’s Security tab and choose “Report a vulnerability.” Keep real secrets out of the report. The security policy explains what to include.
How do updates and rollback work?
Eligible installs can verify and stage signed releases; open-ferry update installs one and open-ferry update -rollback uses the kept previous version. Restart behavior depends on the install and supervisor. A source build reports new releases but does not replace itself. See updates and rollback and the remaining qualification work.
Which versions do these docs cover?
This pre-release page was checked against source snapshot b1d15532, pinned to CLIProxyAPI v8.0.38. The README status and upstream pin describe the development version. Linked main docs evolve; use the matching tag’s docs when testing a candidate.
